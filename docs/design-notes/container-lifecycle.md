# Container lifecycle

Part of the Keep It in Your Box design notes (`docs/design-notes/`). See `CLAUDE.md` for the rules
that reference this.

## Session isolation — canonical `~/.claude`, assembled per launch

Claude Code runs a background-agent daemon arbitrated by `daemon.lock` in its config dir. One shared `~/.claude` across containers broke two ways: separate PID namespaces made the lock's pid/procStart liveness fields meaningless, so daemons displaced each other in a loop; and every container could read every project's transcripts.

An earlier fix split `~/.claude` destructively into a shared dir + a per-project one. That cost the thing a solo user cares about most: afterwards there is no `~/.claude`, so a plain host `claude` has no login and no `--resume` continuity. **Now** `~/.claude` and `~/.claude.json` stay **canonical and stock-untouched**, and per-project isolation comes from *assembling* each container's config from them per launch. Same two path resolvers in the binary, but pointed at per-launch scratch under `$KIB_STATE_ROOT` (`${XDG_STATE_HOME:-~/.local/state}/keep-it-in-your-box`):

| Env var | Resolves | Container path (bind target) | Host source (assembled) |
|---|---|---|---|
| `CLAUDE_CONFIG_DIR` | everything (daemon, sessions, projects, `.claude.json`, history, CLAUDE.md) | `/home/hostuser/.claude-session` | `$KIB_STATE_ROOT/<slug>/session` |
| `CLAUDE_SECURESTORAGE_CONFIG_DIR` | `.credentials.json` + shared assets | `/home/hostuser/.claude-shared` | `$KIB_STATE_ROOT/<slug>/shared` |

The two `.claude-*` names are **container-side only** and unchanged since they were introduced;
only the host end of each bind moved when canonical `~/.claude` was restored. Host-facing text
must use the `$KIB_STATE_ROOT` column.

`<slug>` = `$PWD` with non-alphanumerics → `-` (Claude's own scheme). **Assembly (`assemble_session_dir`, cold-start only — never while a container is attached to these bind-mounted files):**

- **`.claude.json`** — `kib/host/config_scope.py scope-in-json` writes globals + only *this* project's `projects[path]` entry. On exit, `merge-out-json` writes only that subtree back to canonical (globals/other projects byte-untouched; fail-closed on parse error).
- **The subtree is VETTED on the way out, like `settings.json`** (`vet_project_entry`, audit MAC-H2). It went back verbatim for as long as this seam existed, and the asymmetry was the hole: `.claude.json` is box-writable (`claude mcp add` writes it natively), lives outside the FUSE-guarded project tree, and carries `mcpServers`, `allowedTools` and the trust flags that a **host** `claude` — unsandboxed — then reads. So a session could hand the next host session a local `mcpServers.*.command` plus `hasTrustDialogAccepted`. The vet **reduces, never refuses**: rejecting the whole entry would drop the session's ordinary state (mode, onboarding, last session) with the payload. Judged against canonical's current entry, exactly like the git-config validator — the user's own host-side MCP servers and flags round-trip untouched, and only what this session *added* is dropped, named on stderr. Trust flags are one-way: a session may lower one, never raise it — **except `hasTrustDialogAccepted`, exempted 2026-07-28** (`TRUST_FLAGS_EXEMPT`). The box reassembles its config from canonical every cold start, so a folder trusted only inside kib re-prompted and re-raised that flag on every launch: the refusal warned at every teardown and could never converge, and a control that fires on every exit of the normal workflow is one the user stops reading — a real escalation would have printed in the same shape. The accepted cost is that a session can now pre-trust the folder for the next **host** `claude`; since `.claude/settings.json` is box-writable (mixed-use, watched), that chain is now *detected* by `audit_project_configs` rather than refused. The `hasTrustDialog*` prefix still guards any sibling Claude adds later, and `enableAllProjectMcpServers` is unchanged. The converging alternative — grant the trust once host-side, so `scope-in` carries it in and the vet sees it in `prior` — stays available and needs no code. `allowedTools` and `enabledMcpjsonServers` clamp to what canonical had, which costs nothing real because the box runs `--dangerously-skip-permissions` and never prompts (`enabledMcpjsonServers` belongs with them and not with the booleans: `.mcp.json` is writable from the box, so approving a name there is how a session hands a host `claude` a `command` the `mcpServers` vet never sees). Refusal **reverts, never deletes** — a session that *edits* a server the user set up host-side gets the edit dropped and canonical's own entry left standing, or the vet would quietly destroy real config on every exit.
- **Host key vs box key — one key** — the sidecar binds the redacted view at the project's *host* path, so Claude's resolved cwd is that path and canonical and the session share a key. `config_scope`'s verbs therefore take one project path; the second, re-keying argument (and `_rekey_history` with it) was deleted 2026-07-28 — remove the mismatch, never translate it. They diverged only while the view was mounted in-container (no `$PWD` bind, `$HOST_HOME` a symlink to the container home), and `kib_legacy_box_pwd` survives purely to find transcripts stranded under that old key. `macos.md`.
- **`history.jsonl`** — `seed-history` filters to this project's lines in; `merge-history` appends new lines back out (append-only, so a concurrent host `claude` append can't be lost).
- **`CLAUDE.md`** — `place_user_claude_md` copies the user's canonical `~/.claude/CLAUDE.md` straight into the session dir, and nothing else: an in-box edit is transient by design, and canonical stays pure user memory (a host `claude` never sees the policy). *Not* farmed by the entrypoint any more.
- **The sandbox policy is not in that file.** `add_policy_args` binds `guest/policy/etc-CLAUDE.md` `:ro` over `/etc/claude-code/CLAUDE.md` — Claude's **managed-policy** path, which loads ahead of user and project memory, cannot be dropped by a repo's `claudeMdExcludes`, and is not writable by the session (the config dir is). It was concatenated into the assembled `CLAUDE.md` until then, which had all three weaknesses. The rejected alternatives: a `@path` import (still user-scope and writable, and imports load at launch, so it saves no context either); a user rule under `rules/` (same, plus `rules` is not in `config_scope`'s manifest); `--append-system-prompt` (must be passed every invocation, so a `claude` started by hand inside `kib exec bash` runs without it). Missing policy file → `die`: a box whose agent never sees the rules is worse than no box. The image pre-creates `/etc/claude-code` only, so policy edits need a relaunch, not a rebuild.
- **`projects/<slug>`** — an rw bind of `~/.claude/projects/<slug>` at `/run/kib/transcripts`, symlinked into place, so transcripts + `--resume` are shared host⇄box. The bind SOURCE uses the host slug, the symlink NAME the box slug. **Migrate before relinking:** on the first launch after that rename a REAL directory sits at the box slug — Claude had been writing its transcripts there while the link pointed at the host slug — and `bind_via_link` `rm -rf`s a non-symlink, so its contents are folded into `~/.claude/projects/<host-slug>` first. If the fold does not complete the relink is skipped: unlinked transcripts beat deleted ones.
- **Shared assets** — `settings.json`/`keybindings.json` are **copied** into the shared-assembly dir, never bound from canonical (`stage_shared_settings`), and folded back on exit only after the copy passes `settings_findings` (`merge_out_shared_settings`); `plugins/ skills/ agents/ commands/ hooks/` bound **ro** at `/run/kib/shared/<asset>` (the cross-project / host-exec guard — `--unlock-shared` makes them rw so an install lands in canonical for every project + the host claude). A lock-witness file bound ro **only when locked** lets `running_unlocked` read the lock state off the mounts even for a user with no assets to probe.
- **No bind may nest inside those two dir mounts** — `bind_via_link` mounts flat under `/run/kib/` and drops a symlink to it in the parent's host-side dir instead (dangling on the host, resolved in the box). Docker Desktop aborts the whole `docker run` on a nested bind: runc resolves the mountpoint through the parent, lands on the engine VM's `/run/host_virtiofs` view and rejects the path as outside the rootfs — unconditionally, so pre-creating the mountpoint does not help. It also ends the root-owned-leftover-mountpoint class of bug. Not under `/kib`: the entrypoint chmods that 700 root to fence the real project. The synthetic broker credential is bound flat the same way (`:ro` — a mode bit is a no-op on `fakeowner`). `tests/check/portability.sh` fails on a reintroduced nest.
- **Everything else** (daemon, sessions, file-history, caches, and *anything kib doesn't recognise* — `classify`'s drift canary logs it) stays container-private in the session base. **Fail-closed:** an unknown store can't leak and can't touch canonical.

**`~/.claude` → the session dir (entrypoint).** Claude's plugin state stores *absolute host* paths (`installed_plugins.json`'s `installPath`, `known_marketplaces.json`'s `installLocation`) in files farmed from the **read-only** shared mount, so Claude cannot rewrite them to container paths. Without the symlink every host-installed plugin dangles: enabled in `settings.json`, marketplace present, nothing in `/mcp`. It is placed at **`$USER_HOME/.claude`**, not `$HOST_HOME/.claude`: with no `$PWD` bind, the whole-home symlink above always fires, so `$HOST_HOME` is *always* our symlink to `$USER_HOME` and the two paths are the same directory — the `$HOST_HOME` spelling only ever fired when `$HOST_HOME` happened to be a real dir, which it no longer is. The `$USER_HOME` spelling also covers a host user already called `hostuser`. Regression-guarded in `regressions.sh`.

Merge-out runs on the **last terminal out**, after the container is stopped (files quiescent), under a `flock` on `~/.claude.json.lock`. `ensure_claude_home` skeletons a missing `~/.claude` so the binds don't fail on a fresh install.

### Editing a host script under a live session breaks *that* session, not the tree

Two failures that look like bugs and are not, both seen together on 2026-07-28 while this repo was being edited from inside its own sandbox:

- **`_mcp_secrets: command not found`**, for a `warn_inline_mcp_secrets` call that is intact on disk. `bash` does not slurp a script; it reads and executes incrementally, remembering a **byte offset**. Shorten `bin/kib` (or any sourced `host/*.sh`) while a `kib` is running and the next read resumes at an offset that is now mid-token, so the shell executes a suffix of an identifier. The corruption is proportional to the bytes removed *above* the point still to be executed, which is why it surfaces near the end of a launch.
- **`kib.host.config_scope: merge-out-json needs 3 argument(s), got 4`**. A launch sources `host/*.sh` **once**, but `kib_py` execs a **fresh** python from the bind-mounted `kib/` tree every call. Change an argv contract on both sides and the running session pairs the OLD bash with the NEW python. `cli.dispatch` checks arity exactly, so it fails loudly rather than silently mis-scoping — and the merge-out is fail-closed, so canonical is left untouched. The cost is that one session's `projects[…]` subtree and `↑` history are not folded back.

Neither is reproducible from a fresh launch, and both are invisible to `./dev.sh check` (which reads the tree, not a running process). **Diagnose from a new session; never from the one the edit landed under.** `tests/check/wiring.sh`'s "every `_scope` call passes the argument count `cli.dispatch` demands" is what catches the second class *in the tree* — it exists because dropping an argument on one side alone had already shipped once.

## One container per project

Two terminals on the **same** project must work. Claude's own `[concurrentSessions]` registry and daemon arbitration assume all sessions share a PID namespace and `/tmp` — true on the host, false across containers (each reads the other's pid against its own `/proc`, concludes it's dead, displaces it forever; the daemon's own `/tmp/cc-daemon-<uid>/` socket — Claude Code's, not kib's — is container-local too). So:

- **One long-lived container per project** (`kib-<basename>-<hash>`), PID 1 = `sleep infinity` under `--init`. Every terminal attaches via `docker exec`, re-entering the entrypoint. Claude sees one PID namespace, one `/tmp`, one daemon, N sessions — its own arbitration handles the rest.
- **Not `--rm`.** `teardown_container` removes it explicitly (`docker stop` then `docker rm -f`, and every cold start calls that before `docker run`, so a leftover never blocks the name). With `--rm` the engine reaped a container that died during startup before `wait_for_container_ready` could read its logs, and the entire diagnostic was `Error response from daemon: No such container` — which is how a one-line entrypoint bug cost a whole debugging round.
- **Readiness = a process whose argv is *exactly* `sleep infinity`** — only exists after the entrypoint `exec`s. Exactness is load-bearing: mid-setup argv is `/bin/sh …/guest/entrypoint/docker-entrypoint.sh sleep infinity` and PID 1 carries the string forever, so a substring match calls a half-set-up container ready.
- **Lifecycle refcounted with `flock`** on `$KIB_STATE_ROOT/.locks/<slug>.lock`: each terminal holds a **shared** lock (fd 200); `<slug>.boot.lock` (fd 201, exclusive) serialises check-and-create; on exit each tries the lock exclusively — only the last one out succeeds and tears down (then merges out, under fd 203). Locks live outside the container-mounted session dir on purpose (a sandboxed Claude could delete them from inside).
- **Lock files are never unlinked** — tested in place with `flock -n`. Deleting a lock file whose inode another process holds lets the next process lock a fresh inode: two "exclusive" holders.
- **Every backgrounded host process must close fds 200/201** (`200>&- 201>&-`). A child inheriting fd 200 that outlives its `kib` keeps the shared lock held; last-one-out can never lock exclusively, teardown never runs, containers strand. Shipped **twice** without it — the Wayland notifier, then the background image rebuild (`host/image.sh`), which outlives the session by the length of a docker build. The symptom looks nothing like a locking bug: sessions exit cleanly and `docker ps` still lists everything. `regressions.sh` discovers every background job in the launch path and asserts both closes — but closing **by number is not sufficient on macOS**: bash 3.2 saves an fd redirected on a *function call* to a dup >=10 for the post-call restore and leaves close-on-exec off it, so `detach_pgrp`'s child inherited the lock as fd 10. That stranded the clipboard bridge holding the lock for life, and since teardown is what kills the bridge, teardown could never run. `detach_pgrp` now closes fds 3..255 before `exec`, so the guarantee is the shim's, not the caller's. bash >=4 sets close-on-exec on fds >9, which is why this was macOS-only and why `shims.sh` probes fd 3. `docker exec -d` children are exempt. To find a live holder: `lsof $KIB_STATE_ROOT/.locks/<slug>.lock`.
- **Killing a detached process group goes through `kill_pgrp` (`host/portable.sh`), never a hand-rolled `kill -TERM "-$pid"`.** A pidfile records a *number*, and the moment the detached child exits the kernel is free to hand that number to anyone — near-sequentially on Linux, so typically to the **next** launch. `kill -TERM -$pid` then signals whatever group now owns it, and because launches are what create those pids, the group it named was `kib`'s own: the second launch SIGTERMed *itself* one line into `teardown_container`, immediately after the shared-config banner. No message (SIGTERM prints nothing), no container, shell prompt straight back — it reads exactly like a `set -e` abort, which is where the hunt goes first and finds nothing. `kill_pgrp` refuses our own pgid and requires the pid to still *lead* its group, which a recycled number almost never does. Four hand-rolled copies existed (Wayland notifier, clipboard bridge, broker notifier, asset watcher); two never even checked that the value was numeric. `regressions.sh` asserts the pattern appears nowhere but `portable.sh`.
  The trigger was the paired bug: **a script started by `detach_pgrp` gets a fresh environment, and `bin/kib` does not export `KIB_ROOT`** (`host/_load.sh` only sees it because it is *sourced*). `shared-watch.sh` opened with `: "${KIB_ROOT:?…}"`, so it died in milliseconds on every launch — the notifier never fired once, and the fresh corpse of a pid is what armed the group kill. Executed host scripts derive `KIB_ROOT` from `$0`; guarded too.
- `kib` traps **SIGHUP and SIGTERM** and exits through the normal path — bash treats both as fatal *without* running the EXIT trap, so closing a terminal window would otherwise skip teardown.
- `KIB_FORCE_NEW_SESSION=1` = clean slate: own container, own ephemeral config dirs under `$KIB_STATE_ROOT/<slug>.ephemeral.<pid>/` (own daemon, **merge-out disabled** — discarded on exit), own `/tmp/kib-wl.<hash>.eph.<pid>` clipboard scratch dir — sharing the project's would kill the real container's Wayland proxy on its startup-clean and its exit. (Redaction needs no scratch: the mount lives and dies inside the container.)
- **Stale-rules refusal:** redaction is fixed at container creation, so `kib` refuses to attach if `.kibignore` changed since the container started, or if this project's FUSE sidecar is not running — which is also how a container left behind by a kib that mounted the view in-container is caught, since it has no sidecar at all. Same pattern for the `--unlock-shared` mode mismatch.
- **Per-terminal settings ride the `docker exec`, not the container** (`kib_run_session`): `KIB_SESSION_TAG`, and `KIB_NODE_VERSION` for `kib --node-version=NN`. Three things fall out for free — two terminals can hold two different Node versions against ONE container, nothing has to be recreated, and it works against a container created before the setting existed. Note what this is **not**: the `--unlock-shared` and stale-rules refusals above exist because those are *mounts*, fixed at creation, where a mismatch would leave a session looking protected while it is not. A Node version is neither fixed at creation nor a security claim, so adding an attach-refusal for it would be cargo-culting the shape without the reason. The version is applied as a `PATH` prepend rather than an `nvm alias`: `$HOME` is shared by every terminal, so an alias would leak, and only `PATH` reaches non-interactive shells (Claude's own tools, `npx` MCP servers, hooks) — which nvm, being a shell function, never could. What a switch carries is decided by *where a tool was installed*, not by the flag: `npm`/`npx` ship inside the node tarball and follow it, the baked lines each carry their own `pnpm` (see `architecture.md` — pnpm is the one global that crashes on a node below its floor), and everything else in `/usr/bin` is a `#!/usr/bin/env node` script that runs under whichever node PATH resolves. A global installed into the *system* prefix is never shadowed by a switch — that is what made a single system-wide pnpm 11 crash under `nvm use 20`. The versions themselves come from a **user-level cache** (`host/node.sh`), not the image: fetched once per machine, shared by every project, mounted `:ro`. The mount is added unconditionally and is a live view of the host directory, so a version cached later — by another terminal or another project — appears inside containers that already exist. That is the second half of why no attach has to be refused over a Node version: it is neither fixed at creation nor a security claim. Baking the lines into the image was tried first and removed at ~1.0 GB; the cache costs one ~30 s fetch per version per machine and nothing thereafter.

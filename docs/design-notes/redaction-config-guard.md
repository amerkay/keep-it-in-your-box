# Redaction and host-executed config guard

Part of the Keep It in Your Box design notes (`docs/design-notes/`). See `CLAUDE.md` for the rules
that reference this.

## Redaction (.ccignore, FUSE, pre-commit)

- **`ccignore-fuse.py`** runs in a sidecar (`--cap-add=SYS_ADMIN --device /dev/fuse`, host uid) mounting a redacted view at `/tmp/cc-fuse.*/mnt`; the main container mounts *that* at `$PWD` with `:rslave`. Matched paths refuse writes (EACCES) — including files created after launch, which no bind mount can cover. Gitignore-consistent matching with `!` negations (last match wins). Runs for **every** project (it also enforces `global.ccignore`). If `/tmp` isn't a shared mount or the sidecar fails, `cc` **aborts** — no fallback mode.
- **`ccignore-precommit.py`** — installed into `$PWD/.git/hooks/pre-commit` (pre-existing non-managed hooks left alone; detected via `MARKER: ccignore-precommit`). Aborts commits whose staged paths match `.ccignore` (catches already-tracked files, which `.gitignore` can't). Also audits for host-executed config — dangerous `git config` keys (read with `--includes` so `include.path` indirection is expanded), the same keys in bare/nested git dirs found by layout, executable hooks in nested git dirs. That audit is a **detector, not a preventer** (`core.fsmonitor` runs at `git add`, before any hook); the FUSE guard is the preventer. Bypassable with `--no-verify`.
- **Reads through the view can truncate at a 16 KiB boundary — measured, and the reason `dev.sh lint` "flakes".** `shfmt -d cc-lib.sh` (103 KB, 7 read chunks) reports a phantom diff in ~5% of runs: its input ended at **exactly 16384 bytes**, mid-comment, and shfmt's streaming parser had taken that for EOF. Control: the same file with the same `.editorconfig` **off** the mount failed 0/120, on the mount 3/60. It never surfaces as an I/O error, only as nonsense from whatever happened to be reading — a clean file reported unformatted, a `check.sh` grep missing a helper that is plainly there (`_login_ok_after_probe`), `ld.so` asserting on a binary loaded out of the tree. That is why it went years misfiled as flakiness.
  **Fix applied: passthrough I/O is `os.pread`/`os.pwrite`, never `lseek` + `read`/`write`.** With `nothreads=False` several worker threads serve one open file and share that fd's single file offset, so a racing `lseek` can leave a read starting at EOF and returning **0 bytes** — which the kernel reports as EOF, truncating exactly at a chunk boundary. That is sufficient to explain the measurements and `pread` removes it (the offset rides in the syscall). **Confirmed on the first container to run the fixed sidecar**, against the two reproducers that failed hardest before: `./dev.sh lint` went 4/12 and 6/15 failures → **0/20**, and the 13-file `shfmt -d` loop 2/40 → **0/40**. (Note the failure rate is load-dependent — a bare 60× `shfmt -d cc-lib.sh` loop can pass on the *unfixed* code, so measure with `dev.sh lint`, not a single quiet file.) Regression-guarded in `check.sh`; do not "simplify" it back to seek-then-read.
  A second hazard of the same class is **left open** deliberately: `release()` closes the fd while another worker thread may still be in `read()` on it, so a concurrent `open()` can reuse that number and serve another file's bytes. `pread` does not address it — it needs refcounting or a per-handle lock, and neither is testable from inside the sandbox.
- **`.ccignore` → `.gitignore` sync** — managed block (bare names → match-anywhere, `/`-rules → root-anchored; leading-`/` and `..` rules skipped). Idempotent; skipped with a note when launched from a repo subdir.

## Host-executed config guard

The sandbox's real boundary is **what the host runs later**, not the container (the Nov 2025 Cursor/Codex/Antigravity escape shape: hook config, task config, git metadata indirection). The guard reuses the `.ccignore` machinery: one rule tuple `(neg, pattern, anchor, action, immune)`, one matcher, one `_verdict()` loop. `global.ccignore` has `[protect]` (read through, deny writes) and `[redact]` sections; guard rules are **immune to project negation** (guard and project rules tally separately, guard wins) and **tail-matched** (any depth). The guard may negate itself — `.env.*` redacts broadly, `!.env.example` lets placeholders through; enumerating exceptions is the only tractable direction (placeholder names are a closed set, secret variants open-ended).

- **`.git/config` is content-validated, not blocked** (`protect` action). Git writes `config.lock` then renames, so **the rename is the write** — validation needs no write() buffering. Refused only if the write *adds or changes* an entry naming a command the host runs (`core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `alias.*`, `filter.*.clean`, …), compared against the current file (a repo's existing git-lfs filter is the user's own config). Unreadable/non-UTF-8 fails closed.
- **`include`/`includeIf` refused like a command key** (an included file can carry `core.hooksPath` the validator never sees); only *newly added* includes are refused. The parser follows git's grammar — git resumes scanning after `]`, so `[core]hooksPath = x` on one line is a real setting; `_dangerous_entries` must parse the remainder.
- **Git paths matched structurally** (`_git_sensitive()`), not by pattern: submodules nest config/hooks under `.git/modules/<name>/`, worktrees under `.git/worktrees/<name>/`. Shares `_is_git_config()` with the write validator, so "what is a git config" is defined once — which is why `global.ccignore` lists `.vscode`/`.envrc` but not `.git/*`.
- **A git dir is recognised by layout (`HEAD`+`objects`+`refs`), never by the name `.git`** — bare repos, `--separate-git-dir`, and `.git` gitfiles all put config+hooks elsewhere. `_is_git_config()` carries the structural test so `rename()` routes a bare repo's config to the *validator* (not blanket deny) and in-container `git worktree add` works. Gitfiles stay writable; their target is guarded.
- **`link()` validates the source, not only the new name** — a hardlink is a second entry for the same inode and the VFS doesn't re-resolve it, so guarding the target alone let an unmasked alias write `.git/config` or read a redacted `.env` past the stub. (Symlinks re-resolve, so they were never a bypass.)
- **The `.git/hooks` `:ro` bind mount stays as belt-and-braces but is insufficient alone**: conditional on the dir existing at launch, top-level repo only, and `core.hooksPath` routes past it anyway.
- **`no-new-privileges`** on the main container (image ships setuid binaries; defence in depth). Deliberately **not** on the FUSE sidecar (needs `SYS_ADMIN` + `fusermount3`).

## Shared config surface (cross-project pivot)

The canonical `~/.claude` assets (`plugins/ skills/ agents/ commands/ hooks/`) nest-bind into every project's container and auto-load in its next session (and the host `claude`) — the widest blast radius in the design, and not covered by the FUSE guard (which views the *project*, not `$HOME`). The container-side path is still `/home/hostuser/.claude-shared/<asset>`; the host source is now canonical `~/.claude/<asset>`, bound from a per-launch shared-assembly dir.

- Assets mounted **read-only, individually** (nested `:ro` binds over the writable shared-assembly mount — the whole dir can't be `:ro`: `settings.json`/`keybindings.json` stay writable for `/config`, and the credential file needs rewriting). `--unlock-shared` makes them rw, so an install lands in canonical `~/.claude` for every project + the host claude.
- The entrypoint builds a **per-project merge farm** for the asset directories: a real dir with one symlink per shared item (`farm_dir`). Shared items load; in-session creations land in `$CLAUDE_CONFIG_DIR` and work immediately — without this, `/agents`, skill authoring, and `/plugin install` would break and the lock would read as a bug. Pruning removes only symlinks into `$CLAUDE_SHARED_DIR`. State files need no special case (temp+rename replaces the symlink locally); *directories* do — `farm_dir` runs one level deeper on `plugins/{marketplaces,cache,data}` so `/plugin install` can `mkdir` inside.
- **`cc --unlock-shared`** (or `CC_UNLOCK_SHARED=1`) drops the `:ro` mounts — the deliberate promote-to-all-projects path. Mounts fix at creation, so `cc` refuses cross-mode attach (both directions).
- **`settings.json` is staged as a writable COPY, vetted on the way back out.** The refused key set (`_settings_bad_keys`): `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`, `env.ANTHROPIC_{BASE_URL,API_KEY,AUTH_TOKEN}`, `statusLine.command`, inline `hooks.*[].hooks[].command` (the exact bypass making a read-only `hooks/` insufficient — same shape as `core.hooksPath`). Locking the file was rejected (`/config` and theme changes are normal), so the box writes a copy in `$SHARED_BASE` and `merge_out_shared_settings` gates its return to canonical (a refused copy is moved aside to `settings.json.rejected`, out of the way of the next launch's re-stage, and the warning names *that* path); `validate_shared_settings` still vets canonical at launch. **Do not go back to binding canonical `settings.json` rw** — that let a sandboxed session write the file a *host* `claude` loads (host code execution), with the launch-time check firing only after the fact, too late for a host `claude` run in between. Regression-guarded in `check.sh`; no vet (no python3) means no fold-back. **Staging unlinks the destination before copying**, and so does `stage_credential`: these paths used to be single-file bind mounts, so Docker created the mountpoint *inside* `$SHARED_BASE` as **root** — `cp` over that residue fails EACCES, and the symptom is oblique (box silently starts from default settings, `/config` read-only, and the leftover empty file is then "not valid JSON" on the way out, so nothing folds back). Unlink works where write does not, because the directory is the user's.

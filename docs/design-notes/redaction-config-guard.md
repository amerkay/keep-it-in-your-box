# Redaction and host-executed config guard

Part of the Keep It in Your Box design notes (`docs/design-notes/`). See `CLAUDE.md` for the rules
that reference this.

## Redaction (.kibignore, FUSE, the audit gate)

- **`kib/guest/fuse.py`** runs in its own **sidecar** container (`prepare_redaction`, host/redaction.sh), as the host user, with `--network none` and `--cap-drop=ALL --cap-add=SYS_ADMIN`. It mounts a redacted view of the project under a shared-propagation root, and the agent's container binds that view over `$PWD` with `:rslave` — so the agent's container needs no mount capability of its own and there is no unredacted path to the project in it. Matched paths refuse writes (EPERM) — including files created after launch, which no bind mount can cover. Gitignore-consistent matching with `!` negations (last match wins). Runs for **every** project (it also enforces `guest/policy/global.kibignore`). If the view does not come up, kib **refuses to launch** — no fallback mode. Where the propagation root may live, and why: `macos.md`.
- **The audit gate** (`host/gitguard.sh` + `kib/host/gitaudit.py`) — the same two audits, run where kib already runs instead of from a hook written into the user's repo. Dangerous `git config` keys (read with `--includes`, so `include.path` indirection is expanded), the same keys in bare/nested git dirs found by layout, executable hooks in nested git dirs, and tracked paths matching `.kibignore` (which `.gitignore` cannot catch, since they are already in the index).

  Two severities (refuse vs warn), why a hook was never an option, and the accepted loss are all in `kib/host/gitaudit.py`'s module docstring — the canonical statement. It runs at cold start, at last-session teardown (where findings also raise a desktop alert), and on demand via `kib audit` — never on attach, so a second terminal stays instant.
- **Passthrough I/O is `os.pread`/`os.pwrite`, never `lseek` + `read`/`write`.** With `nothreads=False` several worker threads serve one open file and share that fd's single file offset, so a racing `lseek` can leave a read starting at EOF and returning 0 bytes — the kernel reports EOF and the read truncates at a chunk boundary. `pread` carries the offset in the syscall, which removes the race. Regression-guarded in `check.sh`; do not "simplify" it back to seek-then-read.
  **Failure mode to recognise:** never an I/O error, only nonsense from whatever was reading — a clean file reported unformatted, a `check.sh` grep missing a helper that is plainly there, `ld.so` asserting on a binary loaded out of the tree. Rate is load-dependent (~5% under `dev.sh lint`, near zero on a single quiet file), so measure with `dev.sh lint`, not one reader.
  A second hazard of the same class is **left open** deliberately: `release()` closes the fd while another worker thread may still be in `read()` on it, so a concurrent `open()` can reuse that number and serve another file's bytes. `pread` does not address it — it needs refcounting or a per-handle lock, and neither is testable from inside the sandbox.
- **The view must page-cache, and must not recompute the rule verdict per op.** Reported as a 128x slowdown on `node_modules` workloads: 2.31 ms per small file against 0.018 ms on the host, `stat` at 1.50 ms/file, ~95 MB/s bulk, and a Nuxt cold build at 7 minutes against 20 seconds — throughout which `GET /` answers `HTTP 503 "Starting Nuxt…"` instantly, which is indistinguishable from a hang and cost the reporter hours before it was identified as throughput. Three causes, three fixes, all in `kib/guest/fuse.py`:
  - **`auto_cache` on the mount.** Without it libfuse leaves `keep_cache=0` and the kernel drops a file's page cache on **every open**, so a re-read crosses userspace in full and never gets faster — the diagnostic signature is pass 2 matching or beating pass 1 (measured 2311 → 2394 ms). Build tools re-read the same modules many times per run, so this multiplies. `auto_cache` keeps the pages and revalidates mtime+size at open. **Never `kernel_cache`**: it never revalidates, and the project is bind-mounted from the host, so it would serve the user their own stale bytes after an edit in their editor.
  - **`_verdict` is memoised.** `_classify` re-asks it for every ancestor of every `getattr`, `open` and **`read`**, and `rules.verdict` itself re-walks ancestors × rules × `fnmatch` — 0.48 ms per call at `node_modules` depth, ~3 calls per small-file open+read, so roughly half the per-file cost was recomputing an answer that cannot change. Safe by construction, not by luck: the rule list is frozen for the container's lifetime and a mid-session `.kibignore` edit refuses the next attach rather than reloading. **Cache the rule verdict only.** `_classify`'s own `lexists`/`isdir` must stay live — freezing those restores the phantom `.env.local` and its restart loop (below).
  - **`flush()` does not `fsync`.** libfuse calls `flush` on every `close(2)`, so it was a forced writeback per file including read-only opens, and it bought nothing: writes are `os.pwrite` straight to the backing fd with no userspace buffer, and `release()`'s mirror size check reads the same kernel's view either way.

  Measured after, in-sandbox, 1000 files ≤32 KB: **2.31 → 0.067 ms/file** (0.092 cold), `stat` 1.50 → 0.056 ms/file, and sequential re-reads 1623 → 7953 → 8705 MB/s where they had been flat. `auto_cache` cannot help a first read, so the cold-pass gain is the memo and the dropped `fsync`; the pass-2 gain is `auto_cache`. Correctness was probed rather than reasoned about — 200 same-size rewrites in a tight loop all read back fresh, so the float `st_mtime` fusepy reconstructs `tv_nsec` from (~238 ns resolution at the current epoch) is not a staleness risk, and `use_ns` is not worth the churn through `getattr`/`_stub_attr`/`utimens`.
- **The sidecar must raise its own `RLIMIT_NOFILE`, because its fd table is the container-global ceiling on open project files.** Every `open` under the mount holds an fd in that one python process, so its *soft* limit caps how many files **every process in the box together** can hold open in the project tree. containerd's default is soft **1024** / hard 524288, and `raise_fd_limit()` (`kib/guest/fuse.py`) lifts soft to hard at startup — self-tuning, so no number lives in the tree, and the resulting `nofile=1024->524288` is printed on the startup line the failure path already dumps via `docker logs`. Reported as `pnpm generate` (nitro prerender, ~198 routes) dying with dozens of `[500] EMFILE: too many open files` **naming project paths**, non-deterministically; measured ceiling 1019–1020 alone (1024 − the sidecar's own 4) and 502 in a session already holding ~517, which is why it looked like a per-run flake rather than a limit. Verified in-sandbox after the fix, on a fresh container: 400,000 held + 124,284 = **524,284**, i.e. the hard limit less that same overhead of 4.
  **Why it reads as "not the rlimit" and cost the reporter hours:** the limit is invisible from inside the box. **Node raises its own soft limit to the hard one at startup**, and every shell descends from Claude Code, so `ulimit -n` and `/proc/self/limits` both answer 524288 while the container's PID 1 (`sleep infinity`) still shows 1024 — `/proc/1/limits` is the honest reading in-box. Python never raises it, so the sidecar kept the default. Two-process arithmetic is the tell that it is one shared pool, not a leak: 400 held + 619 = 1019, and it recovers fully on close.
  **`--ulimit nofile` on the sidecar's `docker run` is the wrong half of this** — it hardcodes a number kib has to keep in step with the main container's, and the raise belongs where the fds are spent. Don't add both.
- **Don't reach for `FUSE_PASSTHROUGH`** — it is the obvious next lever and it fails the portability contract. The sidecar's kernel is the *container's*: native on Ubuntu, LinuxKit inside Docker Desktop's VM on macOS, the WSL2 kernel on Windows. Passthrough needs **6.9+** with `CONFIG_FUSE_PASSTHROUGH`; Ubuntu 24.04 GA ships 6.8 and WSL2 ships 5.15/6.6, so two of the three floors fail. It also needs libfuse **≥3.17** through the **low-level** API, and fusepy is ctypes over libfuse **2** (`find_library('fuse')` → `libfuse.so.2`, which the Dockerfile pins with `libfuse2t64` for exactly this reason) driven through `fuse_main_real` — it cannot express a backing fd at all. So passthrough is not an alternative to the caching above, it is a rewrite *plus* the caching, on the subset of machines that can run it. The remaining gap after the fixes is ~10x against container-native storage, and that is the fusepy/ctypes/GIL floor: only a compiled low-level server (Rust `fuser`, or libfuse3 — `libfuse3.so.3.17.2` is already in the image) moves it, and that is a from-scratch rewrite of the most security-critical module in the tree.
- **Redaction is format-aware, and there is no second section for it.** A redacted file whose shape a parser can vouch for (dotenv, JSON, YAML) reads as its **key names with every value replaced**; anything else — unknown shape, parse failure, non-UTF-8, over `RENDER_MAX` — keeps the flat stub. This is sandbox-runtime's `extract` masking, taken as the only half worth taking: theirs defaults `onExtractNoMatch: warn`, which fails *open*, and kib's fallback is the stub.
  The reason it is not a security regression but a security *fix*: the stub hid which settings even exist, so the agent's next move was to ask the user, who pasted the real value into the transcript. The stub caused the leak it was preventing.
  - **The rule for `render()`: never pass a byte of the file through.** Output is synthesised from parsed tokens (key names only), so a comment, a continuation, or a value containing `#` or `=` cannot leak by construction. A dotenv value that spans lines bails to the stub — its own interior lines match the key pattern, and a lenient parser would print fragments of the secret as if they were names.
  - **Shape is SNIFFED, never read off the name.** `render()` tries `RENDERERS` in order and takes the first that vouches for the whole file. Dispatching on the name (`*.json`, `.env`, `.env.*`) is what shipped first, and it stubbed every project that spells its secrets file its own way — a real `.kibignore` with `env_vars/env*` and `sls_config/env-*.yml` matched all three rules and rendered none of them, which is precisely the ask-the-user leak above. Order is load-bearing: **dotenv first**, because `A=1` is also a valid YAML scalar and YAML would claim it; **JSON before YAML**, its superset, for the tighter output.
    Sniffing is only safe because each renderer vouches for the file *entirely* — the dotenv one had to stop skipping lines it could not parse, or it would have claimed any prose file holding a single `A=1` and served that one key as though it were the whole content. That strictness has a tail: **one** unparseable line now costs a file all of its keys, which is why `render()` opens `utf-8-sig` — a BOM from a Windows editor is not a reason to stub an ordinary `.env`.
  - **Sniffing costs nothing on the path that matters, and the cheap bails are why.** `render()` is reached only when `_classify` returns `'file'` — a *redacted* path; every ordinary project file goes to `os.pread` and never enters a renderer, so the 0.067 ms small-file figure above is untouched. Within the redacted path it is memoised on `(path, st_ino, st_mtime_ns, st_size)`, so these are per cache **miss**. Measured (libyaml in effect, cache miss, against the old name dispatch): a 40-key dotenv **0.019 ms** (*faster* — the strict bail returns before the old one finished), small JSON 0.006 ms, a 171 B `.pem` **0.003 ms**, a 57 KiB `.pem` **0.062 ms**. A non-UTF-8 file never reaches a renderer at all: the `errors='strict'` open stubs first. The two that are not free are both large *text* files: a 53 KiB colon-heavy log that still stubs (0.478 ms — it passes the colon test and `YAML_MAPPING`, so the parser runs and declines), and a 52 KiB genuine YAML mapping (8.2 ms = 4.3 load + 3.5 emit, and the only one of these that buys something — it renders now where it used to stub). Both are memoised on first touch; neither was worth a second size knob on top of `RENDER_MAX`.
    **Don't drop `":" not in text`** in front of `YAML_MAPPING`: without it every redacted file that ends in the stub pays a whole-file regex scan (~0.6 ms at 57 KiB) against ~0.001 ms for the substring test — that one clause is what makes the `.pem` row above 0.062 ms instead of 0.6 ms.
    **And don't go back to `yaml.safe_load` / `safe_dump`** — they hardcode the pure-python loader even when libyaml is present, which is a ~30x scanner penalty; `yaml.load_all(…, Loader=CSafeLoader)` with the `ImportError` fallback is deliberate.
  - **The YAML renderer bails on an alias, and on a document that is not a mapping.** The loader *expands* aliases, so a billion-laughs file fits inside `RENDER_MAX` many times over and would exhaust the sidecar — container-global, every project file with it — rather than stubbing one file. Nothing has to read the file: `getattr` renders it to report a size, so `ls -l` detonates it, and the result is then held in `_rendered`. The mapping check is the other half: YAML reads almost any text as one big scalar, which would render as a bare `<redacted>` — the flat stub, with a parser's worth of attack surface in front of it. PyYAML is apt's `python3-yaml`, per the CONVENTIONS rule on runtime modules; it is also pinned in `requirements-dev.txt` so the suites can exercise `render()` on a host that has never built the image.
    - **The alias bail reads the EVENT stream, and a regex over the text is NOT good enough — that was tried and shipped broken.** `YAML_ALIAS = (?:^|\s)[&*][A-Za-z0-9_-]` only sees a sigil at string start or after whitespace, and in **flow style** it follows `[`, `{` or `,` instead: `a: [&a [...]]` matched nothing, and a measured **212-byte** file built **1.5 MB** (each added ~40-byte line multiplies by 9). `yaml.parse()` is the one representation that reports an `AliasEvent` *without* expanding it — exact rather than approximate, and linear: 9 levels of the same bomb is 124 events in 0.4 ms where the loader would build ~43M nodes. Regression-guarded with the bomb itself.
    - **The scrub and the dump belong INSIDE the `try`.** A recursive alias (`k: [&x [*x]]`, 13 bytes — also invisible to the old regex) loads fine and then blows the stack in `_scrub`; uncaught, fusepy hands the caller an `EFAULT` it cannot explain instead of the stub. `MemoryError` is caught alongside for the same reason. Same class as `_render_json`'s `RecursionError`, found by review after the first cut got it wrong.
  - **A separate `[mask]` section was designed and thrown away.** Making it a *policy choice* needed a third verdict value, a third branch through `_verdict`/`_classify`, mask/redact/protect precedence, and an enable path threaded from host config into the sidecar's argv — and it left a hostile repo able to select the leakier renderer for its own paths. Keying on **format** instead is one function: format is a property of the file, not something a `.kibignore` can pick.
  - **Accepted residual: a file where the KEY is the secret.** Always on, no switch, no banner — a per-file opt-out is another policy surface for a case the user can solve by not naming a secret in a key.
  - **`getattr` and `read` must share ONE render.** The stub was a constant, so its size was too; a keyed render is content-dependent, and recomputing per call lets a file changing under us report one size and serve another — a partial read then splices two versions together. `Redact._rendered` caches on `(path, st_ino, st_mtime_ns, st_size)`. Same class as the `pread` hazard above: no I/O error, just nonsense from whatever was reading.
- **A masked path the host does not have is `ENOENT`, never a stub** (`_classify` → `'absent'`). Redaction hides *values*; it must not conjure files. Synthesising an entry for a path with no host counterpart made `.env.development`, `.env.local` and `.env.development.local` all stat successfully (256 bytes, mode 0444) in a project holding only `.env` — and `nuxi dev` watches that whole dotenv set, so the phantoms drove an endless restart loop (measured: 6 restarts and +302 log lines in 15 s, permanent `HTTP 503 "Starting Nuxt…"`). Each restart also leaked an inotify instance until `fs.inotify.max_user_instances` (256, not raisable without root) ran out, and *that* surfaces as `EMFILE` on ordinary `open()` calls inside `node_modules` — it reads as an fd-limit problem, with `ulimit -n` at 524288 and ~30 fds open, and cost the reporter hours. `'absent'` is **not** `'pass'`: the read paths fall through to the real syscall and ENOENT exactly as they would outside the box, while `_deny_if_masked` still refuses create/mkdir/rename/chmod there — the box cannot author a `.env.local` through the hole.
  - **A stub's timestamps come from the masked path itself, never from the project root.** A shared root mtime moves whenever any entry is added or removed at top level, so every redacted file in the tree appeared to change at once — the same watcher loop, sustained by the dev server's own build output. Identical-to-the-nanosecond mtimes across unrelated redacted files is the signature. Only synthetic entries under a masked *directory* have no file of their own; they take the directory's.
- **The `.kibignore` → `.gitignore` sync was removed (2026-08-03).** kib wrote a managed block into the repo's own `.gitignore` at every launch, translating the rules (bare names → match-anywhere, `/`-rules → root-anchored). It edited a tracked file the user owns for a benefit the audit gate already delivers better: the gate names **tracked** matches, which is the case `.gitignore` cannot fix anyway, while the block only covered untracked files the user could ignore in one line themselves. Removing it also deletes the emitter's whole class of edge cases — the `!.env` opt-out that must not be mirrored, the subdir-launch skip, the legacy `ccignore` marker strip. Existing blocks are left in place; they are inert and the user can delete them. **Don't reinstate it**: writing to a repo's `.gitignore` is the user's call, and the session can say which line to add.
- **The authoring semantics are in the policy text, because the near-miss is silent.** An agent in an unrelated workspace wrote a `.kibignore` of `**/*.pem`-style rules to hide a dev MySQL data dir and its TLS keys. Every one of them was a no-op past depth 2: a `/`-bearing rule is EXACT-anchored, so `**` equalises to one segment (`_rule_matches`), and the bare name it should have written is already the match-anywhere form. Nothing reports this — `parse()` warns only on `/`-leading and `..` rules, and to the sidecar's stderr, which the box cannot read; the file looks like it worked. Hence the two sub-bullets under "Redacted" in `guest/policy/etc-CLAUDE.md`: the `**` trap, directory sealing (`dir` + `!dir/keep` cannot re-include), and that the rules are frozen at container creation — an edit leaves the live layer on the old set and makes the next attach refuse (`_refuse_if_rules_stale`). **Don't "fix" it by teaching the matcher a recursive glob** — gitignore-shaped is the contract the guard file depends on; the fix was telling the session what the syntax is.

## Host-executed config guard

The sandbox's real boundary is **what the host runs later**, not the container (the Nov 2025 Cursor/Codex/Antigravity escape shape: hook config, task config, git metadata indirection). The guard reuses the `.kibignore` machinery: one rule tuple `(neg, pattern, anchor, action, immune)`, one matcher, one `_verdict()` loop. `guest/policy/global.kibignore` has `[protect]` (read through, deny writes) and `[redact]` sections; guard rules are **tail-matched** (any depth) and tallied separately from a project's, so `[protect]` is **immune to project negation**. The guard may negate itself — `.env.*` redacts broadly, `!.env.example` lets placeholders through; enumerating exceptions is the only tractable direction (placeholder names are a closed set, secret variants open-ended). The set is deliberately **three** — `.example`, `.sample`, `.template`. Each entry is a file the agent reads in full, so it holds only spellings that are always a committed template; `.env.defaults` and `.env.dist` were carried and withdrawn (2026-07-27) because both also see real per-environment use, and the asymmetry is the whole argument: a wrong guess here leaks a secret, a wrong guess the other way costs one "ask the user".
  - **A carve-out has to name the write SIBLING, not just the target** (2026-07-29). Exempting `.env.example` alone made it readable but not editable: nothing writes a file in place, so the refusal landed on a name the caller never chose — `EPERM … open '.env.example.tmp.170.e4cc80fbd4d5'` — and the failure reads as a guard bug rather than a policy. Claude Code's Edit/Write build `${target}.tmp.${pid}.${rand}` (several spellings in the bundle, all `.tmp.`-prefixed) and rename; vim's `writebackup` is **on** by default and opens `${target}~`. Both fall back through the three negations into `.env.*`. So each placeholder carries `!<name>.tmp.*` and `!<name>~`, and the rename that finishes the job is already fine (its target is exempt). Read risk is nil by construction — the only content that can occupy `<placeholder>.tmp.*` is an in-flight copy of the placeholder.
  - **`[redact]` is opt-out-able, `[protect]` is not** (2026-07-30). A project `.kibignore`'s `!` on the **same path component** cancels a `[redact]` guard rule — `!.env` hands that file to the session in full from the next container on. The split is the two tiers' threat models, not their danger: `[protect]` stops the box writing what the **host** later executes, and no repo may waive that; `[redact]` withholds *the user's own secrets from the user's own session*, which is theirs to waive, and plenty of `.env` files are ports and feature flags. Refusing outright had the same shape as the stub-vs-render argument above — the agent asks, and the user pastes the value into the transcript instead.
    - **Same component, deliberately.** `verdict()` records the level at which the guard matched and the level of the last project `!`, and cancels only when they are equal — otherwise `!secrets` (or a stray `!*`) would un-redact every `.env` beneath it in passing, which nobody writing that rule intended.
    - **The control is that the user SEES it, so keep it quiet enough to be read.** The box can write `.kibignore`, so a session that read a hostile repo can smuggle a `!.env` in and collect it at the next launch; `.kibignore` is frozen at container creation, so the user is present for that launch. `report_kibignore_optouts` (host/redaction.sh, via `rules.redact_optouts`) prints one `ℹ️` line per opt-out rule at **every** launch — rules, not a tree walk, so it says the same thing before the file exists. Deliberately not an alarm: on the projects that use this it is a standing setting, and a warning shown every launch is one nobody reads. A host-only opt-out (in `~/.keep-it-in-your-box/config`, which the box cannot write) would close that gap and was weighed against it costing a host-terminal edit per project; if the printed line ever proves too easy to miss, that is the fallback, not a louder banner.
  - **Not `.env.example*`.** The obvious one-glob fix re-admits `.env.example.local`, which is deliberately redacted (a real per-environment spelling) — an open-ended prefix for a closed-set problem, the `.env.dist` argument a second time. The carve-out is the temp *shape*, and the shape alone carves nothing: `.env.tmp.170.abc` and `.env.local~` stay redacted, and a rename from an exempt temp onto a secret-bearing target is refused at the target.

- **`.idea/` was withdrawn from `[protect]` (2026-07-30), and it is a known hole, not a cleanup.** It broke `pnpm install` in a JetBrains project: the install writes under `.idea/`, took the guard's `EPERM`, and the policy text tells the session to *stop and report* on that — so an unrelated everyday command could not finish. That is exactly the "a rule on a file ordinary work edits ends the session over routine work" test the tier is supposed to apply, and `.idea/` fails it. What is now unguarded is real: `.idea/workspace.xml` carries RunManager run configurations and `.idea/watcherTasks.xml` carries File Watchers — JetBrains runs the first on Run and the second on **every save**, unprompted. Not moved to the detection tier either (that would be the natural next step: two regex entries in `TEXT_CONFIGS`, on a file that is gitignored in most repos and therefore dirty at every launch). The stated control is `git diff .idea/`, and re-adding the `[protect]` rule is right for a machine where nothing needs to write there.
- **Two tiers, split by WHEN a file fires: ambient trigger vs deliberate `claude` launch.** `[protect]` refuses the write outright, and the policy text (`guest/policy/etc-CLAUDE.md`) tells the session to *stop and report* on that error — so a guard rule on a file ordinary work edits ends the session over routine work. A rule is therefore only worth it where **no report could arrive in time**: `.githooks`, `.gitmodules`, `.cursor/mcp.json`, `.zed/tasks.json`, `.zed/debug.json`, `.run`, `.mvn/jvm.config`, `.exrc`, `.nvim.lua`, `.ripgreprc`, `.yarnrc.yml`, `.vscode`, `.devcontainer`, `.envrc` — every one fires at the next commit, `cd`, editor-open or ordinary tool invocation, with the user not thinking about Claude at all. Anything that waits for someone to *launch `claude`* is detected instead, because a deliberate act is one a teardown report reaches first.
  - **Superseded wording, kept because the change is recent (2026-08-01):** this used to read "split by how a file is USED, not by how dangerous it is — only **pure-exec** files get a rule", with `.claude/hooks` named as the canonical pure-exec entry. That axis was wrong twice over. It put `.claude/hooks` in `[protect]` even though nothing there loads until a `settings.json`, plugin manifest or skill frontmatter *names* it — so the guard refused the script while the pointer that arms it stayed writable, protecting nothing — and it blocked the one sanctioned way to ship a repo-local committed hook, since a plugin's hooks live at `<plugin root>/hooks/hooks.json`. Withdrawn, and detected tree-wide instead.
  - **The project-tree detector unions git with an mtime stamp**, and the mtime half is not belt-and-braces. `_dirty()` is a proxy for "changed during a session", and the box can `git commit` — so it decides what "tracked" means, and a committed hook checks out pristine past any dirty-file filter. That is precisely the bypass that got `feat/worktree-editor-carveout` reverted, so a tree-shaped detector cannot rely on git alone. `_since_stamp()` (`--hooks-stamp`, refreshed *after* reporting at launch and teardown) does not care what git thinks. No stamp yet reports nothing: hooks already in a fresh clone are the user's own, the same judgement `audit_nested_hooks` makes about the top-level `.git/hooks`.
  - **A `plugin.json` pointer is followed one level, and only inwards.** `hooks`/`mcpServers`/`lspServers`/`experimental.monitors` may each be a path string rather than the block itself, so aiming one at an unremarkable file is otherwise a way to declare a hook the audit never reads. One hop, never two — a manifest must not be able to walk the scanner around the filesystem — and a pointer resolving outside the repo is named and never opened. The resolver is `asset_scan.pointer_paths`, shared with the shared-tree scan so the two cannot drift on what a pointer is.

- **Mixed-use** config — `.claude/settings*.json`, `.mcp.json`, `.zed/settings.json`, `.cargo/config.toml`, `mise.toml`, `.pre-commit-config.yaml` — stays writable and is *detected* instead, by `audit_project_configs()` in the audit gate. Blanket-protecting them was specified and rejected: rename-validation (what makes `.git/config` writable-but-checked) only works because git writes a lockfile and renames, and Node's `writeFileSync` does not — so a `[protect]` rule on `.claude/settings.json` would break Claude Code's own "always allow" persistence with no validated path to replace it.
  - **`.mcp.json` is detected, never refused**, because `intercept_mcp_add` (host/mcp.sh) deliberately passes a credential-free stdio `mcp add` through to the in-box write: that IS the supported path for a plain `npx` server, and refusing it would leave none. It is also the weakest chain here — Claude Code prompts before enabling a project server.
  - **`.yarnrc.yml` is the one judgment call in the protect tier.** It is mixed-use (`yarn set version` writes `yarnPath`), but neither side can validate it: the guest ships fusepy only and the host is python 3.9, so there is no YAML parser to check it with. Refused, on the grounds that `yarnPath` runs arbitrary JS at the next `yarn` and setting it is normally a host action.
  - **File-precision inside `.cursor/` and `.zed/`**, never the directory. `.cursor/rules` and `.claude/commands` are prompt text, which kib holds is not execution — the same line the shared-assets tier draws.
  - The detection tier reports a path only when `git status --porcelain` shows it **dirty or untracked**. The audit sees state, not change, and a committed config is the user's own; without the filter it would warn every launch and train the user to ignore it. **Ignored counts as untracked here** — plain `status` hides a gitignored path, and `.claude/settings.local.json`, the file Claude writes "always allow" into, is ignored in most repos (or by the user's global excludes), so the highest-traffic config of the set was the one this tier could never see. `--ignored` is scoped by a `:(glob)**/<name>` pathspec per config name: repo-wide it would enumerate every path under `node_modules`, and a vendored copy is pruned anyway (it loads only if the user works from in there). The gap hid behind the environment: CI and the box carry no global excludes, so the suite passed in both and failed only on a developer's own machine. Its regex checks (`.cargo/config.toml`, `mise.toml`, `.pre-commit-config.yaml` — no `tomllib` on 3.9, no YAML parser anywhere) are acceptable *because this tier only warns*: a false positive costs one line of output, not a refused write. They match pivot keys only — `[hooks]` and `_.source` fire on a bare `cd`; a mise `[tasks]` entry or a cargo alias runs when the user invokes it by name, which is the "someone chose to" line again.
- **A kib refusal is `EPERM`; an ordinary permission failure is `EACCES`.** The reason a write was refused is logged by the FUSE server to the *sidecar container's* stderr, which the agent cannot see — so the errno is the only channel that can say which layer said no. `REFUSED` in `kib/guest/fuse.py` is the single definition; `default_permissions` keeps returning EACCES for a genuine owner/mode failure, so the two stay distinguishable.
- **`.git/config` is content-validated, not blocked** (`protect` action). Git writes `config.lock` then renames, so **the rename is the write** — validation needs no write() buffering. Refused only if the write *adds or changes* an entry naming a command the host runs (`core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `alias.*`, `filter.*.clean`, …), compared against the current file (a repo's existing git-lfs filter is the user's own config). Unreadable/non-UTF-8 fails closed.
- **`include`/`includeIf` refused like a command key** (an included file can carry `core.hooksPath` the validator never sees); only *newly added* includes are refused. The parser follows git's grammar — git resumes scanning after `]`, so `[core]hooksPath = x` on one line is a real setting; `git_ini_entries` must parse the remainder.
- **Match git's input NORMALISATION, then fall closed on anything still ambiguous** (audit MAC-C2/H1). Grammar was not enough: git drops a leading UTF-8 BOM and ends a line at `\n` only (folding `\r\n`), while `str.strip()` leaves a BOM in place — it is not whitespace — and `str.splitlines()` also breaks on `U+2028/2029/0085`, VT, FF and FS/GS/RS. So `<BOM>[core]fsmonitor = …` read as one ordinary key and flagged nothing, and `[filter "<U+2028>x"]clean = …` split into two harmless-looking lines for the parser and stayed one live driver for git. `git_ini_entries` now normalises the way git does; if any divergent character survives that, it parses the body **both** ways, unions the findings and adds `AMBIGUOUS_ENTRY` so the write is refused whichever reader is right. Refusing the class beats chasing spellings — no real config carries these. The standing recommendation is still to stop hand-parsing and diff `git config --file <candidate> --list --includes`; it was not taken here because that runs `git` from inside the FUSE handler, against a path the same sidecar serves.
- **Git paths matched structurally** (`_git_sensitive()`), not by pattern: submodules nest config/hooks under `.git/modules/<name>/`, worktrees under `.git/worktrees/<name>/`. Shares `_is_git_config()` with the write validator, so "what is a git config" is defined once — which is why `guest/policy/global.kibignore` lists `.vscode`/`.envrc` but not `.git/*`.
- **A git dir is recognised by layout (`HEAD`+`objects`+`refs`), never by the name `.git`** — bare repos, `--separate-git-dir`, and `.git` gitfiles all put config+hooks elsewhere. `_is_git_config()` carries the structural test so `rename()` routes a bare repo's config to the *validator* (not blanket deny). Gitfiles stay writable; their target is guarded.
- **A guarded path may be REPRODUCED at a nested path, never authored** (`_mirror_anchor`, `kib/guest/fuse.py`). A `[protect]` write below the project root is admitted iff its bytes are identical to the same guarded tail **at the root** — `.claude/worktrees/w/.vscode/settings.json` must match `./.vscode/settings.json` exactly. The root copy has no shorter guarded suffix than itself, so it is never its own mirror and stays absolutely immutable; because the box cannot write it, its bytes are the host's own, and reproducing what the host already executes grants no capability. A payload differs from its anchor, or has none, and is refused.
  - **The problem it solves:** a checkout *is* a write, so a repo that both tracks and guards a path could not be checked out in the box at all — `git worktree add` died on `cannot create directory at '.vscode'`, and the same hit `git clone`, a branch switch and `stash pop`. Not scoped to worktrees, deliberately: the rule is a property of the bytes, so it covers all four uniformly with no new location, tier or allowlist to keep in step.
  - **Why no carve-out keyed on "tracked" or on a worktree root can work.** An earlier attempt (branch `feat/worktree-editor-carveout`, reverted) exempted `.vscode`/`.idea`/`.devcontainer` under `.claude/worktrees/`. It was bypassable with **zero detection**: `git add`/`git commit` work in the box, so the box decides what "tracked" means — commit a `.vscode/tasks.json` with `runOptions.runOn: folderOpen` on a branch, `worktree add` it, and the checkout is pristine. Its `audit_worktree_configs` detector filtered on dirty-or-untracked and saw nothing, and `audit_tracked` only fires if the project's own `.kibignore` names `.vscode`. Opening the agent's worktree to review its work is normal, so that is a live host-RCE path. **Do not reintroduce one.**
  - **Enforced at four points, all fail-closed:** no anchor → refuse; anchor absent on disk → refuse; any differing byte in `write()` → refuse *before* it lands, so nothing partial is ever on disk; final size ≠ the anchor's at `release()` → **unlink**, then refuse. That last one is what write() cannot see — a prefix of a script matches byte for byte as far as it goes, and `rm -rf /tmp/x` truncated to `rm -rf /` is a different command. The **unlink is the enforcement there**: the kernel does not reliably surface a `release()` error to `close()`, so leaving nothing behind is what actually holds and the errno is a courtesy.
  - **`mirror_ok=False` at every op that moves bytes the guard never compared** — `rename` (both ends), `symlink`, `link` (both ends), `truncate`. A mirror is creatable through create+write only. Without this, writing the payload to an unguarded name and renaming it onto a guarded one skips the content check entirely; a symlink's content is a path, a hardlink's inode keeps changing after the check, and a standalone truncate can only produce a *short* copy.
  - **git's own paths are excluded before the suffix walk** (`_git_sensitive` first). `.git/config` and `.git/hooks/*` fire on an ordinary git command with nobody asking, so "the host runs identical bytes elsewhere" is not a reason to allow one — and a repo carrying a root `config` or `hooks/` twin would otherwise make them mirrorable. Regression-guarded on **order**, not presence. `[redact]` is excluded too: a copy of a secret is still the secret.
  - **Deleting a mirror is allowed; deleting an anchor is not.** `git worktree remove` needs it, and it is safe for the same reason the write is: the only thing that can come back is the anchor's own bytes. The nested-path relaxation is the whole cost — a nested guarded file whose root twin exists became deletable, where before nothing guarded was.
  - **`GIT_TEMPLATE_DIR=` is set on the container** (`host/lifecycle.sh`). Mirrors do not help `git clone`/`git submodule add`, which failed for a different reason: git copies its sample hooks from the template, and creating a `.git/hooks/` the host executes is exactly what the guard refuses. The samples are all disabled examples, so an empty template loses nothing. The test fixtures used this workaround inline for a long time before it moved to the launch.
- **`link()` validates the source, not only the new name** — a hardlink is a second entry for the same inode and the VFS doesn't re-resolve it, so guarding the target alone let an unmasked alias write `.git/config` or read a redacted `.env` past the stub. (Symlinks re-resolve, so they were never a bypass.)
- **The `.git/hooks` `:ro` bind mount is gone** — `$PWD` *is* the FUSE view now, so a bind over a subpath of it would shadow the layer doing the enforcing. It was never sufficient anyway: conditional on the dir existing at launch, top-level repo only, and `core.hooksPath` routed past it. The guard covers what the bind never could — nested repos, submodules, and repos created mid-session.
- **`no-new-privileges`** on the agent's container (image ships setuid binaries; defence in depth). Nothing in it mounts, so there is no conflict to reason about — the sidecar is a separate container and does not carry the flag.

## Shared config surface (cross-project pivot)

The canonical `~/.claude` assets (`plugins/ skills/ agents/ commands/ hooks/`) bind into every project's container and auto-load in its next session (and the host `claude`) — the widest blast radius in the design, and not covered by the FUSE guard (which views the *project*, not `$HOME`). The container-side path is still `/home/hostuser/.claude-shared/<asset>`, now as a symlink to the flat `/run/kib/shared/<asset>` bind (nested binds abort the run on Docker Desktop — `macos.md`); the host source is canonical `~/.claude/<asset>`.

Assets mount **individually**, never the whole dir (`settings.json`/`keybindings.json` stay writable for `/config`, and the credential file needs rewriting), and since 2026-08-01 in **one open tier** — `KIB_ASSETS_OPEN` in `host/config.sh`:

- **All five are writable and symlinked straight at canonical.** A skill, agent, command, hook or plugin created inside a box lands in `~/.claude`, where every project and a host `claude` get it — which is the entire point of authoring or installing one. The entrypoint plants one symlink per tree and nothing else.
- **The `:ro` lock on `plugins/` + `hooks/` was deleted, and this is a deliberate trade, not a cleanup.** It cost mount-mode selection, a lock witness bound only when locked, `running_unlocked`, a cross-mode attach refusal, the `unlock-shared` verb, and a per-project symlink **farm** with a depth table (`cache` 2, `data` 1, `marketplaces` 0), a prune walk, a `temp_git_*` sweep and a bounded chown that existed only to keep the macOS cold start off a 100k-entry plugin cache — about 460 lines, all removed. What it bought was never complete either: `~/.claude/skills/` was already writable, and any folder under a skills directory containing `.claude-plugin/plugin.json` loads as a plugin at personal scope with **no marketplace and no install step**, so the lock never covered the obvious relocation.
  - **What that accepts, stated plainly** (audit H6, moved Split → Accepted): a poisoned `plugins/x/hooks/hooks.json` written from repo A's box auto-runs unattended in repo B's box at its next launch, with repo B's source bind-mounted rw. No host `claude` is involved, so the host-gated warning is silent on exactly that machine. The reasoning is that the pivot is box→box — in-container execution, the class already accepted for H3/H4 — and not host RCE.
- **`kib/host/asset_scan.py` is now the whole control**, so it is wider than the version that only had to keep three prompt trees text-only. It reports: any `hooks`/`mcpServers`/`lspServers`/`monitors`/`experimental` **`command`** (`AUTO_RUN_KEYS`); a `monitors.json`, which is a bare JSON *array* with no arming key anywhere above it and is therefore armed **by filename**; a `.claude-plugin/plugin.json` and its one-hop pointers; a marketplace clone's `.git/config` and executable `.git/hooks`, neither of which is JSON and both of which were invisible before; and a symlink out of the tree.
  - **A symlink out of the tree is a READ primitive, not an exec one** (audit MAC-M1). These trees are host-backed and outside the FUSE view, so `skills/x/SKILL.md -> ~/.ssh/id_rsa` persists into canonical, auto-loads in every future session *and* in the host's own unsandboxed `claude`, and the loader follows it and ingests the target — content the box cannot read itself, fetched for it by the host. `asset_scan` checks dirs as well as files (the walk is `followlinks=False`, so a symlinked *directory* is only ever seen once, right there) and never opens a link it has flagged, which would pull the target's bytes into the scanner's own output. In-tree links pass: that is ordinary skill plumbing.
  - **The line is auto-execution, not executability.** Refusing the exec bit or a `#!` was specified and thrown away before it shipped: the first real shared skill on the author's machine bundles two executable Python helpers, and most non-trivial skills ship one — the rule would have flagged `skills/` permanently on first contact and read as a bug. It buys nothing either, because a bundled script runs only if the agent decides to run it, and a skill that is pure prose saying "now run this installer" is identical in effect and undetectable.
  - **Change-scoped against a stamp** (`scan-new`), because unscoped it reports every legitimately installed plugin on every exit — an alarm that is always on — and walks 100k+ cache entries to do it (~30s over macOS virtiofs). Two details are load-bearing, and both are the same asymmetry: kib owns the stamp, the sandbox owns the files.
    - **`changed_at`, not `st_mtime`.** These trees are writable from a session, so mtime is the payload's to choose — one `touch -d 2000-01-01` and it drops out of the scan that is the entire control. Files are compared on `max(mtime, ctime)`; ctime moves on every write and no unprivileged writer can wind it back. The *stamp* is read as plain mtime: it lives in host-only `$STATE_DIR`, outside every bind, so nothing in a box can move it. Same treatment in `gitaudit._since_stamp`, for the same reason.
    - **Its own stamp, refreshed after the scan** (`assets.scanned`), never `report_shared_asset_writes`' `assets.seen`. That one is refreshed by every launch of every project, so sharing it meant a second terminal opening mid-session moved the reference point past what the session had already written into `plugins/` or `hooks/` — trees that report has never covered. It is seeded (not refreshed) on a first launch, so the first teardown after upgrading reports this session rather than every plugin already installed.
    - **`kib audit` forces a WHOLE scan**, stamp or no stamp: it is a look the user just typed, and answering "nothing changed since your last launch" to "what is in my shared trees" is answering a different question.
  - **Teardown only, and gated on a native `claude` actually existing.** The finding matters most while the user still remembers the session that wrote it, and the one reader outside a sandbox is a host install — so `host_claude_path()` (`host/portable.sh`, memoised, deliberately **not** `npm prefix -g`: that spawns node on a launch path for one line of prose) gates the whole check, not just its wording. No host claude, no walk, no output. `kib audit` forces it on demand.
  - **Accepted gaps.** Hooks declared in a skill's or agent's **YAML frontmatter** are missed: python 3.9 has no YAML parser and the host side must run on stock macOS (`macos.md`). Prose saying "now run this installer" is undetectable, as it always was. And it is detection, not prevention — a plain bind mount offers nothing to interpose on.
- **`host/shared-watch.sh` is gone.** A first-write inotify alert was content-blind, and with `plugins/` writable it fired on ordinary plugin-cache churn (`.in_use/134`) — noise that trains the user to ignore the alert that matters. `report_shared_asset_writes` still names what changed since the last launch, scoped to the **prompt** trees for the same cost reason as above, and its stamp is per-*state-root*, not per-project: the trees are global, so "changed since any box last started" reports each change once instead of once per project.
- **There is no migration, deliberately.** A project used before the collapse holds real per-project entries in these trees, and `ln -sfn` cannot replace a non-empty dir — so the entrypoint leaves that dir alone and it keeps shadowing the shared tree for that one project. Nothing is lost and nothing moves: reinstalling the skill or plugin is what shares it. Two fold-out functions (~95 lines in `host/config.sh`) did the migration entry-by-entry for the prompt trees and whole-tree for `plugins`/`hooks`; they were deleted 2026-08-01 with the rest of the compat layer. Re-adding one is only worth it if kib ever has users who cannot be told to reinstall.

- **The box's config dir mounts at the HOST's own `~/.claude` path** (`SESSION_CDIR`, host/lifecycle.sh) — `/home/kay/.claude`, `/Users/veronica/.claude`, never a fixed `/home/hostuser` spelling. Claude records `installLocation`/`installPath` absolute and *validates* them against the running config dir, so any other spelling makes it reject the state canonical hands it (`corrupted installLocation … expected a path inside …`, and the marketplace refresh refuses). Canonical is shared with the host `claude` and can only hold host paths, so the box agrees on the spelling instead: nothing to translate, and every recorded field is covered including ones upstream adds later. Re-rooting the fields at assembly was built and thrown away — a JSON rewrite keyed to upstream field names, plus its tests, to make two paths agree that could just *be* the same path. Mount source is still the per-project scratch dir, so isolation is unchanged. A project inside `~/.claude` steps aside to the old spelling: the `$PWD` bind would otherwise nest inside this one and abort the whole run (`macos.md`).
- **`settings.json` is staged as a writable COPY, vetted on the way back out.** Locking the file was rejected (`/config` and theme changes are normal), so the box writes a copy in `$SHARED_BASE` and `merge_out_shared_settings` gates its return to canonical; a refused copy is moved aside to `settings.json.rejected` (out of the way of the next launch's re-stage — the warning names *that* path). `validate_shared_settings` still vets canonical at launch. No vet (no python3) means no fold-back.
- **Do not go back to binding canonical `settings.json` rw.** That let a sandboxed session write a file the *host* `claude` loads — host code execution, with the launch-time check firing only after the fact, too late for a host `claude` run in between. Regression-guarded in `check.sh`. The refused key set is `settings_findings` (`kib/shared/dangerous.py`): the auth helpers (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`), the `ANTHROPIC_*` and interpreter/loader `env` keys, `statusLine.command`, and inline `hooks.*[].hooks[].command` — that last one is the exact bypass that makes a read-only `hooks/` insufficient, same shape as `core.hooksPath`. **Add auth helpers and loader-env keys as FAMILIES, not one spelling at a time:** `gcpAuthRefresh` (the Vertex sink of CVE-2026-35022) and the framework/fallback/versioned `DYLD_*` keys were each the one sibling left out of a set that was otherwise complete, and each was a live path on a host configured for it (audit MAC-H3/L1).
- **Staging unlinks the destination before copying**, and so does `stage_credential`. These paths were single-file bind mounts once, so Docker may have left a **root-owned** mountpoint inside `$SHARED_BASE`; `cp` over it fails EACCES and the symptom is oblique (box starts from default settings, `/config` read-only, the leftover empty file then fails to parse on the way out so nothing folds back). Unlink works where write does not, because the directory is the user's.

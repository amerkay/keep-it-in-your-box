# Redaction and host-executed config guard

Part of the Keep It in Your Box design notes (`docs/design-notes/`). See `CLAUDE.md` for the rules
that reference this.

## Redaction (.kibignore, FUSE, the audit gate)

- **`kib/guest/fuse.py`** runs in its own **sidecar** container (`prepare_redaction`, host/redaction.sh), as the host user, with `--network none` and `--cap-drop=ALL --cap-add=SYS_ADMIN`. It mounts a redacted view of the project under a shared-propagation root, and the agent's container binds that view over `$PWD` with `:rslave` — so the agent's container needs no mount capability of its own and there is no unredacted path to the project in it. Matched paths refuse writes (EPERM) — including files created after launch, which no bind mount can cover. Gitignore-consistent matching with `!` negations (last match wins). Runs for **every** project (it also enforces `guest/policy/global.kibignore`). If the view does not come up, kib **refuses to launch** — no fallback mode. Where the propagation root may live, and why: `macos.md`.
- **The audit gate** (`host/gitguard.sh` + `kib/host/gitaudit.py`) — the same two audits, run where kib already runs instead of from a hook written into the user's repo. Dangerous `git config` keys (read with `--includes`, so `include.path` indirection is expanded), the same keys in bare/nested git dirs found by layout, executable hooks in nested git dirs, and tracked paths matching `.kibignore` (which `.gitignore` cannot catch, since they are already in the index).

  Two severities (refuse vs warn), why a hook was never an option, and the accepted loss are all in `kib/host/gitaudit.py`'s module docstring — the canonical statement. It runs at cold start, at last-session teardown (where findings also raise a desktop alert), and on demand via `kib audit` — never on attach, so a second terminal stays instant. A cold start still removes the obsolete hook if it carries kib's old `MARKER: ccignore-precommit`, and leaves any other hook strictly alone.
- **Passthrough I/O is `os.pread`/`os.pwrite`, never `lseek` + `read`/`write`.** With `nothreads=False` several worker threads serve one open file and share that fd's single file offset, so a racing `lseek` can leave a read starting at EOF and returning 0 bytes — the kernel reports EOF and the read truncates at a chunk boundary. `pread` carries the offset in the syscall, which removes the race. Regression-guarded in `check.sh`; do not "simplify" it back to seek-then-read.
  **Failure mode to recognise:** never an I/O error, only nonsense from whatever was reading — a clean file reported unformatted, a `check.sh` grep missing a helper that is plainly there, `ld.so` asserting on a binary loaded out of the tree. Rate is load-dependent (~5% under `dev.sh lint`, near zero on a single quiet file), so measure with `dev.sh lint`, not one reader.
  A second hazard of the same class is **left open** deliberately: `release()` closes the fd while another worker thread may still be in `read()` on it, so a concurrent `open()` can reuse that number and serve another file's bytes. `pread` does not address it — it needs refcounting or a per-handle lock, and neither is testable from inside the sandbox.
- **Redaction is format-aware, and there is no second section for it.** A redacted file whose shape is known (`*.json`, `.env*`) reads as its **key names with every value replaced**; anything else — unknown shape, parse failure, non-UTF-8, over `RENDER_MAX` — keeps the flat stub. This is sandbox-runtime's `extract` masking, taken as the only half worth taking: theirs defaults `onExtractNoMatch: warn`, which fails *open*, and kib's fallback is the stub.
  The reason it is not a security regression but a security *fix*: the stub hid which settings even exist, so the agent's next move was to ask the user, who pasted the real value into the transcript. The stub caused the leak it was preventing.
  - **The rule for `render()`: never pass a byte of the file through.** Output is synthesised from parsed tokens (key names only), so a comment, a continuation, or a value containing `#` or `=` cannot leak by construction. A dotenv value that spans lines bails to the stub — its own interior lines match the key pattern, and a lenient parser would print fragments of the secret as if they were names.
  - **A separate `[mask]` section was designed and thrown away.** Making it a *policy choice* needed a third verdict value, a third branch through `_verdict`/`_classify`, mask/redact/protect precedence, and an enable path threaded from host config into the sidecar's argv — and it left a hostile repo able to select the leakier renderer for its own paths. Keying on **format** instead is one function: format is a property of the file, not something a `.kibignore` can pick.
  - **Accepted residual: a file where the KEY is the secret.** Always on, no switch, no banner — a per-file opt-out is another policy surface for a case the user can solve by not naming a secret in a key.
  - **`getattr` and `read` must share ONE render.** The stub was a constant, so its size was too; a keyed render is content-dependent, and recomputing per call lets a file changing under us report one size and serve another — a partial read then splices two versions together. `Redact._rendered` caches on `(path, st_ino, st_mtime_ns, st_size)`. Same class as the `pread` hazard above: no I/O error, just nonsense from whatever was reading.
- **`.kibignore` → `.gitignore` sync** — managed block (bare names → match-anywhere, `/`-rules → root-anchored; leading-`/` and `..` rules skipped). Idempotent; skipped with a note when launched from a repo subdir.
- **The authoring semantics are in the policy text, because the near-miss is silent.** An agent in an unrelated workspace wrote a `.kibignore` of `**/*.pem`-style rules to hide a dev MySQL data dir and its TLS keys. Every one of them was a no-op past depth 2: a `/`-bearing rule is EXACT-anchored, so `**` equalises to one segment (`_rule_matches`), and the bare name it should have written is already the match-anywhere form. Nothing reports this — `parse()` warns only on `/`-leading and `..` rules, and to the sidecar's stderr, which the box cannot read; the file looks like it worked. Hence the two sub-bullets under "Redacted" in `guest/policy/etc-CLAUDE.md`: the `**` trap, directory sealing (`dir` + `!dir/keep` cannot re-include), and that the rules are frozen at container creation — an edit leaves the live layer on the old set and makes the next attach refuse (`_refuse_if_rules_stale`). **Don't "fix" it by teaching the matcher a recursive glob** — gitignore-shaped is the contract the `.gitignore` emitter and the guard file both depend on; the fix was telling the session what the syntax is.

## Host-executed config guard

The sandbox's real boundary is **what the host runs later**, not the container (the Nov 2025 Cursor/Codex/Antigravity escape shape: hook config, task config, git metadata indirection). The guard reuses the `.kibignore` machinery: one rule tuple `(neg, pattern, anchor, action, immune)`, one matcher, one `_verdict()` loop. `guest/policy/global.kibignore` has `[protect]` (read through, deny writes) and `[redact]` sections; guard rules are **immune to project negation** (guard and project rules tally separately, guard wins) and **tail-matched** (any depth). The guard may negate itself — `.env.*` redacts broadly, `!.env.example` lets placeholders through; enumerating exceptions is the only tractable direction (placeholder names are a closed set, secret variants open-ended). The set is deliberately **three** — `.example`, `.sample`, `.template`. Each entry is a file the agent reads in full, so it holds only spellings that are always a committed template; `.env.defaults` and `.env.dist` were carried and withdrawn (2026-07-27) because both also see real per-environment use, and the asymmetry is the whole argument: a wrong guess here leaks a secret, a wrong guess the other way costs one "ask the user".

- **Two tiers, split by how a file is USED, not by how dangerous it is.** `[protect]` refuses the write outright, and the policy text (`guest/policy/etc-CLAUDE.md`) tells the session to *stop and report* on that error — so a guard rule on a file ordinary work edits ends the session over routine work. Only **pure-exec** files get a rule: `.githooks`, `.gitmodules`, `.claude/hooks`, `.cursor/mcp.json`, `.zed/tasks.json`, `.zed/debug.json`, `.run`, `.mvn/jvm.config`, `.exrc`, `.nvim.lua`, `.ripgreprc`, `.yarnrc.yml`. **Mixed-use** config — `.claude/settings*.json`, `.mcp.json`, `.zed/settings.json`, `.cargo/config.toml`, `mise.toml`, `.pre-commit-config.yaml` — stays writable and is *detected* instead, by `audit_project_configs()` in the audit gate. Blanket-protecting them was specified and rejected: rename-validation (what makes `.git/config` writable-but-checked) only works because git writes a lockfile and renames, and Node's `writeFileSync` does not — so a `[protect]` rule on `.claude/settings.json` would break Claude Code's own "always allow" persistence with no validated path to replace it.
  - **`.mcp.json` is detected, never refused**, because `intercept_mcp_add` (host/mcp.sh) deliberately passes a credential-free stdio `mcp add` through to the in-box write: that IS the supported path for a plain `npx` server, and refusing it would leave none. It is also the weakest chain here — Claude Code prompts before enabling a project server.
  - **`.yarnrc.yml` is the one judgment call in the protect tier.** It is mixed-use (`yarn set version` writes `yarnPath`), but neither side can validate it: the guest ships fusepy only and the host is python 3.9, so there is no YAML parser to check it with. Refused, on the grounds that `yarnPath` runs arbitrary JS at the next `yarn` and setting it is normally a host action.
  - **File-precision inside `.cursor/`, `.zed/` and `.claude/`**, never the directory. `.cursor/rules` and `.claude/commands` are prompt text, which kib holds is not execution — the same line the shared-assets open tier draws.
  - The detection tier reports a path only when `git status --porcelain` shows it **dirty or untracked**. The audit sees state, not change, and a committed config is the user's own; without the filter it would warn every launch and train the user to ignore it. **Ignored counts as untracked here** — plain `status` hides a gitignored path, and `.claude/settings.local.json`, the file Claude writes "always allow" into, is ignored in most repos (or by the user's global excludes), so the highest-traffic config of the set was the one this tier could never see. `--ignored` is scoped by a `:(glob)**/<name>` pathspec per config name: repo-wide it would enumerate every path under `node_modules`, and a vendored copy is pruned anyway (it loads only if the user works from in there). The gap hid behind the environment: CI and the box carry no global excludes, so the suite passed in both and failed only on a developer's own machine. Its regex checks (`.cargo/config.toml`, `mise.toml`, `.pre-commit-config.yaml` — no `tomllib` on 3.9, no YAML parser anywhere) are acceptable *because this tier only warns*: a false positive costs one line of output, not a refused write. They match pivot keys only — `[hooks]` and `_.source` fire on a bare `cd`; a mise `[tasks]` entry or a cargo alias runs when the user invokes it by name, which is the "someone chose to" line again.
- **A kib refusal is `EPERM`; an ordinary permission failure is `EACCES`.** The reason a write was refused is logged by the FUSE server to the *sidecar container's* stderr, which the agent cannot see — so the errno is the only channel that can say which layer said no. `REFUSED` in `kib/guest/fuse.py` is the single definition; `default_permissions` keeps returning EACCES for a genuine owner/mode failure, so the two stay distinguishable.
- **`.git/config` is content-validated, not blocked** (`protect` action). Git writes `config.lock` then renames, so **the rename is the write** — validation needs no write() buffering. Refused only if the write *adds or changes* an entry naming a command the host runs (`core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `alias.*`, `filter.*.clean`, …), compared against the current file (a repo's existing git-lfs filter is the user's own config). Unreadable/non-UTF-8 fails closed.
- **`include`/`includeIf` refused like a command key** (an included file can carry `core.hooksPath` the validator never sees); only *newly added* includes are refused. The parser follows git's grammar — git resumes scanning after `]`, so `[core]hooksPath = x` on one line is a real setting; `git_ini_entries` must parse the remainder.
- **Match git's input NORMALISATION, then fall closed on anything still ambiguous** (audit MAC-C2/H1). Grammar was not enough: git drops a leading UTF-8 BOM and ends a line at `\n` only (folding `\r\n`), while `str.strip()` leaves a BOM in place — it is not whitespace — and `str.splitlines()` also breaks on `U+2028/2029/0085`, VT, FF and FS/GS/RS. So `<BOM>[core]fsmonitor = …` read as one ordinary key and flagged nothing, and `[filter "<U+2028>x"]clean = …` split into two harmless-looking lines for the parser and stayed one live driver for git. `git_ini_entries` now normalises the way git does; if any divergent character survives that, it parses the body **both** ways, unions the findings and adds `AMBIGUOUS_ENTRY` so the write is refused whichever reader is right. Refusing the class beats chasing spellings — no real config carries these. The standing recommendation is still to stop hand-parsing and diff `git config --file <candidate> --list --includes`; it was not taken here because that runs `git` from inside the FUSE handler, against a path the same sidecar serves.
- **Git paths matched structurally** (`_git_sensitive()`), not by pattern: submodules nest config/hooks under `.git/modules/<name>/`, worktrees under `.git/worktrees/<name>/`. Shares `_is_git_config()` with the write validator, so "what is a git config" is defined once — which is why `guest/policy/global.kibignore` lists `.vscode`/`.envrc` but not `.git/*`.
- **A git dir is recognised by layout (`HEAD`+`objects`+`refs`), never by the name `.git`** — bare repos, `--separate-git-dir`, and `.git` gitfiles all put config+hooks elsewhere. `_is_git_config()` carries the structural test so `rename()` routes a bare repo's config to the *validator* (not blanket deny). Gitfiles stay writable; their target is guarded.
- **A guarded path may be REPRODUCED at a nested path, never authored** (`_mirror_anchor`, `kib/guest/fuse.py`). A `[protect]` write below the project root is admitted iff its bytes are identical to the same guarded tail **at the root** — `.claude/worktrees/w/.vscode/settings.json` must match `./.vscode/settings.json` exactly. The root copy has no shorter guarded suffix than itself, so it is never its own mirror and stays absolutely immutable; because the box cannot write it, its bytes are the host's own, and reproducing what the host already executes grants no capability. A payload differs from its anchor, or has none, and is refused.
  - **The problem it solves:** a checkout *is* a write, so a repo that both tracks and guards a path could not be checked out in the box at all — `git worktree add` died on `cannot create directory at '.vscode'`, and the same hit `git clone`, a branch switch and `stash pop`. Not scoped to worktrees, deliberately: the rule is a property of the bytes, so it covers all four uniformly with no new location, tier or allowlist to keep in step.
  - **Why no carve-out keyed on "tracked" or on a worktree root can work.** An earlier attempt (branch `feat/worktree-editor-carveout`, reverted) exempted `.vscode`/`.idea`/`.devcontainer` under `.claude/worktrees/`. It was bypassable with **zero detection**: `git add`/`git commit` work in the box, so the box decides what "tracked" means — commit a `.vscode/tasks.json` with `runOptions.runOn: folderOpen` on a branch, `worktree add` it, and the checkout is pristine. Its `audit_worktree_configs` detector filtered on dirty-or-untracked and saw nothing, and `audit_tracked` only fires if the project's own `.kibignore` names `.vscode`. Opening the agent's worktree to review its work is normal, so that is a live host-RCE path. **Do not reintroduce one.**
  - **Enforced at four points, all fail-closed:** no anchor → refuse; anchor absent on disk → refuse; any differing byte in `write()` → refuse *before* it lands, so nothing partial is ever on disk; final size ≠ the anchor's at `release()` → **unlink**, then refuse. That last one is what write() cannot see — a prefix of a script matches byte for byte as far as it goes, and `rm -rf /tmp/x` truncated to `rm -rf /` is a different command. The **unlink is the enforcement there**: the kernel does not reliably surface a `release()` error to `close()`, so leaving nothing behind is what actually holds and the errno is a courtesy.
  - **`mirror_ok=False` at every op that moves bytes the guard never compared** — `rename` (both ends), `symlink`, `link` (both ends), `truncate`. A mirror is creatable through create+write only. Without this, writing the payload to an unguarded name and renaming it onto a guarded one skips the content check entirely; a symlink's content is a path, a hardlink's inode keeps changing after the check, and a standalone truncate can only produce a *short* copy.
  - **git's own paths are excluded before the suffix walk** (`_git_sensitive` first). `.git/config` and `.git/hooks/*` fire on an ordinary git command with nobody asking, so "the host runs identical bytes elsewhere" is not a reason to allow one — and a repo carrying a root `config` or `hooks/` twin would otherwise make them mirrorable. Regression-guarded on **order**, not presence. `[redact]` is excluded too: a copy of a secret is still the secret.
  - **Deleting a mirror is allowed; deleting an anchor is not.** `git worktree remove` needs it, and it is safe for the same reason the write is: the only thing that can come back is the anchor's own bytes. The nested-path relaxation is the whole cost — a nested guarded file whose root twin exists became deletable, where before nothing guarded was.
  - **`GIT_TEMPLATE_DIR=` is set on the container** (`host/lifecycle.sh`). Mirrors do not help `git clone`/`git submodule add`, which failed for a different reason: git copies its sample hooks from the template, and creating a `.git/hooks/` the host executes is exactly what the guard refuses. The samples are all disabled examples, so an empty template loses nothing. The test fixtures used this workaround inline for a long time before it moved to the launch.
- **`link()` validates the source, not only the new name** — a hardlink is a second entry for the same inode and the VFS doesn't re-resolve it, so guarding the target alone let an unmasked alias write `.git/config` or read a redacted `.env` past the stub. (Symlinks re-resolve, so they were never a bypass.)
- **The `.git/hooks` `:ro` bind mount is gone** — `$PWD` *is* the FUSE view now, so a bind over a subpath of it would shadow the layer doing the enforcing. It was never sufficient anyway: conditional on the dir existing at launch, top-level repo only, and `core.hooksPath` routed past it. The guard covers what the bind never could — nested repos, submodules, and repos created mid-session.
- **`no-new-privileges`** on the agent's container (image ships setuid binaries; defence in depth). Nothing in it mounts, so there is no conflict to reason about — the sidecar is a separate container and does not carry the flag.

## Shared config surface (cross-project pivot)

The canonical `~/.claude` assets (`plugins/ skills/ agents/ commands/ hooks/`) bind into every project's container and auto-load in its next session (and the host `claude`) — the widest blast radius in the design, and not covered by the FUSE guard (which views the *project*, not `$HOME`). The container-side path is still `/home/hostuser/.claude-shared/<asset>`, now as a symlink to the flat `/run/kib/shared/<asset>` bind (nested binds abort the run on Docker Desktop — `macos.md`); the host source is canonical `~/.claude/<asset>`.

Assets mount **individually**, never the whole dir (`settings.json`/`keybindings.json` stay writable for `/config`, and the credential file needs rewriting), in **two tiers** — the table is `KIB_ASSETS_LOCKED` / `KIB_ASSETS_OPEN` in `host/config.sh`:

- **Locked — `plugins/`, `hooks/`: `:ro`.** These carry a `command` the *host* executes: hook entries, a plugin's bundled MCP servers, and a marketplace clone's own `.git/hooks` (canonical is git-pulled by a host `claude`, and the FUSE guard views the *project*, not `$HOME`). A write is host RCE, so the mount refuses it. `plugins/` is the reason locking `hooks/` alone is not a control — a plugin is a superset of a hook, the same way inline `hooks[].command` in `settings.json` bypasses a read-only `hooks/`, and `core.hooksPath` bypassed a read-only `.git/hooks`. Three spellings of one bug.
- **Open — `skills/`, `agents/`, `commands/`: writable, and genuinely shared.** Prompt text with no executed command. The entrypoint symlinks these straight at the shared tree instead of farming them, so a skill authored inside a box lands in canonical and loads everywhere — which is the entire point of authoring one. `validate_shared_assets` (`kib/host/asset_scan.py`) demotes a tree to `:ro` for the launch if any JSON in it configures a `hooks`/`mcpServers` **`command`**; otherwise a "text-only" tree is just a parking spot for the payload `plugins/` blocks.
  - **A symlink out of the tree is refused too, and it is a READ primitive, not an exec one** (audit MAC-M1). These trees are host-backed and outside the FUSE view, so `skills/x/SKILL.md -> ~/.ssh/id_rsa` persists into canonical, auto-loads in every future session *and* in the host's own unsandboxed `claude`, and the skill loader follows it and ingests the target — content the box cannot read itself, fetched for it by the host. `asset_scan` checks dirs as well as files (the walk is `followlinks=False`, so a symlinked *directory* is only ever seen once, right there) and never opens a link it has flagged, which would pull the target's bytes into the scanner's own output. In-tree links pass: that is ordinary skill plumbing.
  - **Detection, not prevention, and it now runs at teardown as well as launch.** These are plain bind mounts with no layer to interpose on, so nothing can refuse the write itself — the honest ceiling is to say so. Reporting only at the next launch meant a session could plant a skill and the user would hear about it after the next `cc`, possibly in a different project; `validate_shared_assets teardown` names it while they still remember the session that wrote it, and raises a desktop alert — skipping any tree this run's launch scan already named, so a condition the user has chosen to live with is not re-alerted every exit. `launch` mode additionally demotes the tree to `:ro` for that container.
  - **The line is auto-execution, not executability.** Refusing the exec bit or a `#!` was specified and thrown away before it shipped: the first real shared skill on the author's machine bundles two executable Python helpers, and most non-trivial skills ship one — the rule would have demoted `skills/` permanently on first contact and read as a bug. It buys nothing either, because a bundled script runs only if the agent decides to run it, and a skill that is pure prose saying "now run this installer" is identical in effect and undetectable. A `hooks`/`mcpServers` `command` needs no such decision. JSON only: hooks and MCP servers are configured in JSON, and the host has no YAML parser in the 3.9 stdlib.
  - Writes are **reported, not prevented** — same trade as `settings.json`. `host/shared-watch.sh` fires one `notify_desktop` on the first write of a container's life and exits (an exit is cheaper than any throttle); `report_shared_asset_writes` names what changed since the last launch, which is the half a mid-session watcher cannot see — another project's box, or a host process, writing while nothing was attached. Its stamp is per-*state-root*, not per-project, deliberately: the trees are global, so "changed since any box last started" reports each change once instead of once per project.
  - **The migration is a fold-out, and it is not optional.** `ln -sfn` cannot replace a non-empty dir, so a project holding real per-project entries in these trees — which is *every* project used before this change, because the read-only tier sent every in-box install there — silently keeps its private dir, and that dir **shadows the whole shared tree**: one project-local skill hid every other skill from that project, permanently. Leaving it alone therefore fails worse than migrating: the box also reads the policy text saying its writes are global, and they would not be. `fold_out_project_assets` (`host/config.sh`, cold start only — the session dir is bind-mounted, so moving entries out from under a live container makes them vanish mid-session) moves each entry to canonical, drops the old farm's now-dangling symlinks (`-L` as well as `-e`: `-e` follows the link, so testing existence alone skips exactly the entries that block the `rmdir`), never overwrites a name clash, and names everything it moved. The caller re-runs `validate_shared_assets` afterwards, because a folded-in `command` has to demote the tree on *this* launch — `start_container` reads `KIB_ASSETS_DEMOTED` to pick the mount. It promotes what a box wrote per-project to global, which grants nothing the rw mount does not already allow.
  - Two limits, both inherited from where the check runs. Mounts fix at creation, so a **demotion takes effect at the next cold start** — on an attach the warning fires but the running container's rw mount stands (`validate_shared_settings` has the same shape: prevention at launch, not at write). And the scan sees JSON only, so a `command` in some future YAML config would pass; the host has no YAML parser in the 3.9 stdlib and adding a dependency there is out (`macos.md`).
- `--unlock-shared` makes the **locked** pair rw, so an install lands in canonical for every project + the host claude. The open tier is unaffected: it is already writable, so the flag's meaning narrowed to "unlock what the host executes" and `running_unlocked`'s witness-on-the-mounts check needed no change.
- The entrypoint builds a **per-project merge farm** for `plugins/`: a real dir with one symlink per shared item (`farm_dir`). Shared items load; in-session creations land in `$CLAUDE_CONFIG_DIR` and work immediately — without this, `/agents`, skill authoring, and `/plugin install` would break and the lock would read as a bug. Pruning removes only symlinks into `$CLAUDE_SHARED_DIR`. State files need no special case (temp+rename replaces the symlink locally); *directories* do — `farm_dir` takes a per-tree **depth**: `cache` 2 (the installer stages a clone in `plugins/cache/temp_git_*` and renames it onto `cache/<marketplace>/<plugin>/<version>`), `data` 1, `marketplaces` 0 (git clones — no farm makes one writable while its `.git` is `:ro`, so the installer re-clones per-project). Shallower, `cache/<marketplace>` was a symlink into the read-only mount whenever canonical held that marketplace: the rename failed EROFS and `/plugin install` sat on "Installing…" for good, stranding the clone for every later start to re-walk and re-chown — hence the `temp_git_*` sweep at container creation, where nothing can be mid-install. Planting mirror dirs means `prune_farm` must tear them down deepest-first (`rmdir` refuses while project content remains), or a plugin deleted from canonical lingers as a dir of dangling links.
- **The box's config dir mounts at the HOST's own `~/.claude` path** (`SESSION_CDIR`, host/lifecycle.sh) — `/home/kay/.claude`, `/Users/veronica/.claude`, never a fixed `/home/hostuser` spelling. Claude records `installLocation`/`installPath` absolute and *validates* them against the running config dir, so any other spelling makes it reject the state canonical hands it (`corrupted installLocation … expected a path inside …`, and the marketplace refresh refuses). Canonical is shared with the host `claude` and can only hold host paths, so the box agrees on the spelling instead: nothing to translate, and every recorded field is covered including ones upstream adds later. Re-rooting the fields at assembly was built and thrown away — a JSON rewrite keyed to upstream field names, plus its tests, to make two paths agree that could just *be* the same path. Mount source is still the per-project scratch dir, so isolation is unchanged. A project inside `~/.claude` steps aside to the old spelling: the `$PWD` bind would otherwise nest inside this one and abort the whole run (`macos.md`).
- **`kib unlock-shared`** (or `KIB_UNLOCK_SHARED=1`) drops the `:ro` mounts on the locked pair — the deliberate promote-to-all-projects path for a plugin or hook. Mounts fix at creation, so kib refuses cross-mode attach (both directions).
- **`settings.json` is staged as a writable COPY, vetted on the way back out.** Locking the file was rejected (`/config` and theme changes are normal), so the box writes a copy in `$SHARED_BASE` and `merge_out_shared_settings` gates its return to canonical; a refused copy is moved aside to `settings.json.rejected` (out of the way of the next launch's re-stage — the warning names *that* path). `validate_shared_settings` still vets canonical at launch. No vet (no python3) means no fold-back.
- **Do not go back to binding canonical `settings.json` rw.** That let a sandboxed session write a file the *host* `claude` loads — host code execution, with the launch-time check firing only after the fact, too late for a host `claude` run in between. Regression-guarded in `check.sh`. The refused key set is `settings_findings` (`kib/shared/dangerous.py`): the auth helpers (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`), the `ANTHROPIC_*` and interpreter/loader `env` keys, `statusLine.command`, and inline `hooks.*[].hooks[].command` — that last one is the exact bypass that makes a read-only `hooks/` insufficient, same shape as `core.hooksPath`. **Add auth helpers and loader-env keys as FAMILIES, not one spelling at a time:** `gcpAuthRefresh` (the Vertex sink of CVE-2026-35022) and the framework/fallback/versioned `DYLD_*` keys were each the one sibling left out of a set that was otherwise complete, and each was a live path on a host configured for it (audit MAC-H3/L1).
- **Staging unlinks the destination before copying**, and so does `stage_credential`. These paths were single-file bind mounts once, so Docker may have left a **root-owned** mountpoint inside `$SHARED_BASE`; `cp` over it fails EACCES and the symptom is oblique (box starts from default settings, `/config` read-only, the leftover empty file then fails to parse on the way out so nothing folds back). Unlink works where write does not, because the directory is the user's.

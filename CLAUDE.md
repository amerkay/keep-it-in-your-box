# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Docker-based sandbox for running Claude Code in an isolated container. The `cc` script builds and runs a Docker container that mirrors the host user's UID/GID, mounts the current project directory, and forwards Claude's auth/config.

## Working on this repo (read first)

Claude works on `claude-docker` **from inside the sandbox this repo builds**. So:

- **No `docker` binary, no Docker socket.** You cannot build the image, run `cc`, or test a container end to end. Hand those commands to the user as a **fenced block they can paste into a host terminal** — pasteable as-is, no `!` prefix (that runs *in this container*, not on the host), no `$` prompts, no placeholders left to fill in. This matters: a `! findmnt --target /tmp` during the sandbox-escape review reported the *container's* tmpfs as `private`, and the wrong answer nearly drove a redesign until the same command run host-side returned `shared`.
- **`~/.claude-shared/` and `$CLAUDE_CONFIG_DIR` are LIVE host state**, bind-mounted in. Never aim destructive or migration logic at them to "try it". Build a fake `$HOME` under the scratchpad and test against that: `migrate-sessions.sh` keys everything off `$HOME`, and `CC_MIGRATE_TEST=1` disables its safety checks for exactly this purpose.
- **Edits to `cc` / `cc-lib.sh` / `docker-entrypoint.sh` take effect on the user's *next* launch**, never this session. `bash -n` every script you touch before finishing — a syntax error leaves the user unable to start the sandbox at all.
- **"Next launch" means a new *container*, not a new terminal.** One long-lived container serves every terminal on the project, and `./cc` while any session is still open just `docker exec`s into the existing one — so a rebuilt image, an edited entrypoint, and a fixed sidecar all appear to do nothing. The container is recreated only when the **last** session exits (the flock teardown) and a fresh `cc` starts. Sidecars are worse: `wayland-guard.py` and `ccignore-fuse.py` are bind-mounted, so the file on disk is current while the *running* sidecar still executes the code it started with. Check before believing a "no change" result: `ps -o lstart= -p 1` inside the container is the container's real birth time. This has burned a full verification round.

## Architecture

- **`cc`** — Host-side launcher. Owns the launch flow: the sensitive-dir guard, project identity, the lifecycle locks, container create/attach/teardown, and the `docker exec` that runs the session. Run from any project directory; args pass through as the command.
- **`cc-lib.sh`** — Sourced by `cc`, not standalone. The self-contained subsystems: image build + update check, the shared-CLAUDE.md sync, the `.ccignore` → `.gitignore` + pre-commit sync, both `.ccignore` redaction backends, and the live-DNS sync (`add_resolv_sync_args`/`start_resolv_sync`), which keeps a long-lived container's `resolv.conf` in step with the host across wifi/VPN changes (see "DNS across host network changes"). Shares `cc`'s shell, so it also shares its `set -euo pipefail` and globals.
- **`resolv-sync.sh`** — A dependency-free (POSIX sh) watcher run *inside* the main container as a detached root `docker exec`. It polls the read-only bind-mount of the host's `/run/systemd/resolve` and copies the current upstream nameservers into the container's `/etc/resolv.conf` whenever they change, stripping loopback servers and never blanking the file. This is how the container follows the host's live DNS without a relay, a `--network host` sidecar, or a host edit — and it works behind a per-connection host firewall (Portmaster) that would block a relay's `container→gateway:53` hop, since the container queries the real upstreams directly.
- **`wayland-guard.py`** — Filtering Wayland proxy, run in a sidecar that is the only thing holding the real compositor socket. Passes clipboard *reads*, refuses every clipboard *write*. See "Clipboard: mediated, not handed over".
- **`security-test.sh`** — One regression suite for every control the audit established, run **inside** a sandbox (`./security-test.sh`, `--list`, `-k <section>`, `--no-clipboard`). Each check re-attempts a real attack and asserts the refusal, *and* re-attempts the legitimate operation it must not break — a guard that blocks the attack by breaking the workflow has failed too, which is exactly how the clipboard proxy's first version passed review and still broke `wl-paste`. Non-destructive: an exploit is proven dead by showing the write refused *and* the value resolving to nothing, never by detonating a payload or reading a real secret. Fixtures live in `.sectest/` and are **reused, not recreated** — the guard rightly refuses to `unlink` a `.git/config`, so a suite that made fresh repos each run would leave a growing pile of undeletable dirs; clear them from the host.
- **`build-bg.sh`** — Background image rebuild. `flock` on `build.lock` prevents concurrent builds; runs under `setsid` so `kill -TERM -PGID` cancels the whole tree. Desktop notification on completion.
- **`Dockerfile`** — Debian trixie (13), Node.js (NodeSource, major pinned by the `NODE_MAJOR` build arg), Python 3, dev tools, Claude Code via the official installer. `CUSTOM_PACKAGES` adds apt packages; `CACHE_BUST` forces a reinstall. Installed version is recorded in `/etc/claude-code-version`. Also carries the SVG→GIF toolchain (`rsvg-convert`, `cairosvg`, Pillow, alongside the existing `ffmpeg`): prefer **`rsvg-convert`** — it rasterizes through Pango, so a CSS `font-family` *list* resolves, whereas cairosvg goes through cairo's toy font API, which treats the whole comma-separated string as one literal family name, finds no match, and silently falls back to proportional sans. Headless Chrome is **not** a usable rasterizer here: it hangs on GCM registration retries, and `--headless=new`/`--disable-background-networking` don't help.
- **`docker-entrypoint.sh`** — **Baked into the image (`COPY`), unlike `ccignore-fuse.py`/`wayland-guard.py`/`resolv-sync.sh`, which are bind-mounted from `$SCRIPT_DIR`. Editing it needs an image rebuild, not just a relaunch** — a relaunch silently keeps running the old copy. Creates a user matching the host UID/GID, fixes ownership of the mounted config dirs, builds the shared-asset symlink farm (below), sets up Wayland clipboard access, then `exec gosu` to drop privileges. Re-entered by every `docker exec` session, which takes its "already the target user" branch.
- **`migrate-sessions.sh`** — One-time host script splitting a legacy `~/.claude` into `~/.claude-shared/` + `~/.claude-sandbox/<slug>/`, then deleting `~/.claude` and `~/.claude.json`. Dry-run by default; `--apply` commits; `--force` redoes it. On `--apply` it refuses to run while any `cc-*` container or host `claude` process is alive, since a torn copy would be deleted out from under it.
- **`shared-CLAUDE.md`** — Sandbox policy (secrets hard-stop, `.ccignore`, sandbox limits) injected into every session. `cc` syncs it into a marker-delimited block at the top of `~/.claude-shared/CLAUDE.md`; anything the user writes below the block survives.
- **`ccignore-fuse.py`** — FUSE redacting passthrough, run in a sidecar container (`--cap-add=SYS_ADMIN --device /dev/fuse`, as the host uid) that mounts a redacted view of the project at `/tmp/cc-fuse.*/mnt`; the main container mounts *that* at `$PWD` with `:rslave`. Matched paths refuse writes (EACCES) — including files created **after** launch, which no bind mount can cover. Matching is gitignore-consistent, honouring `!` negations (last match wins). It runs for **every** project, not only those with a `.ccignore`, because it also enforces `global.ccignore` (below). Needs `/tmp` to be a shared mount: if it isn't, or if the sidecar fails to mount, `cc` **aborts** rather than run unprotected — there is no fallback mode.
- **`global.ccignore`** — The host-executed-config guard, shipped in this repo and mounted read-only into the sidecar from `$SCRIPT_DIR` (so there is no second copy to keep in step, and nothing for the attach-time staleness check to compare). Rules are **immune to a project's negation** — `_verdict` tallies guard and project rules separately and the guard wins, so a project cannot ship `!.vscode` and switch its own guard off — and **tail-matched**, so a rule matches at any depth. The guard file may negate *itself* (last match wins within the guard set), which is how `.env.*` redacts broadly while `!.env.example` lets the committed placeholder through. Enumerating the exceptions is the only tractable direction: the placeholder names are a closed set, the secret-bearing variants (`.env.local`, `.env.production`, …) are open-ended. Two sections: `[protect]` (read through, deny writes) and `[redact]` (stub on read, deny writes — the existing `.ccignore` behaviour). See "Host-executed config guard" below.
- **`ccignore-precommit.py`** — Host-side git `pre-commit` hook, installed/refreshed into `$PWD/.git/hooks/pre-commit` (a pre-existing non-managed hook is left alone; detected via its `MARKER: ccignore-precommit` line). Aborts any commit whose staged paths match `.ccignore`, keeping sensitive files out of history and diffs on the host. Catches already-tracked files, which `.gitignore` cannot. Also audits the repo for host-executed config — dangerous `git config` keys (read with `--includes`, so `include.path` indirection is expanded rather than read as one benign line), the same keys in *bare and nested* git dirs found by layout, and executable hooks in nested git dirs — which runs whether or not a `.ccignore` exists. That audit is a **detector, not a preventer**: `core.fsmonitor` is executed by git during `git add`, long before any hook fires. The FUSE guard is what actually prevents the write. Bypassable with `--no-verify`.
- **`.ccignore` → `.gitignore` sync** — Mirrors `.ccignore` into a managed block in `.gitignore` (bare names → match-anywhere, `/`-rules → root-anchored; unsafe leading-`/` and `..` rules skipped). Idempotent; preserves the rest of the file. Blocks untracked sensitive files from being staged; the pre-commit hook is the backstop. Skipped with a note when `cc` is launched from a subdir of the repo.
- **`sleep-guard.sh`** — Host-side daemon started by `cc`, one per terminal. Every 3s it samples `wchar` (bytes written) from `/proc/<pid>/io` for the processes of **its own session** and takes the **largest delta by any single process**, inhibiting sleep (`systemd-inhibit`) while that exceeds `SLEEP_GUARD_MIN_BYTES` and releasing after 30s of quiet. It **cannot** use `docker logs`: PID 1 is `sleep infinity` and each session runs under `docker exec`, whose output goes to that terminal's TTY, never the container log stream. The sampling `docker exec` runs as the *host uid* deliberately — `/proc/<pid>/{io,environ}` are gated by `ptrace_may_access`, which root-without-`CAP_SYS_PTRACE` fails against a uid-1000 process, while a same-uid reader passes. When it goes idle **with the lid already shut** it also suspends the machine itself (see "Proactive suspend" below). Tunables: `SLEEP_GUARD_GRACE`, `SLEEP_GUARD_MIN_BYTES`, `SLEEP_GUARD_DEBUG=1`, `SLEEP_GUARD_LID_SUSPEND` (default 1; set 0 to keep working lid-shut without auto-suspend).
    - **Scoped per session, never the whole container.** One container serves every terminal on the project, so a container-wide sample makes *one* working session inhibit on behalf of *all N* terminals — three tabs, three locks, one earned. `cc` stamps its `docker exec` with a unique `CC_SESSION_TAG`; claude's tools and subagents inherit it across fork/exec, so matching `/proc/<pid>/environ` answers "is this pid ours" with no ppid walk and no pid registry to keep in step. The tag is set on the **exec**, not the container, so it is per-terminal and works against a container created before the tag existed. It is passed to the sampling shell as `CC_GUARD_TAG` (a different name) so that shell's own environ cannot match the pattern and count itself as activity.
    - **Busiest process, never the sum.** The sum is what pinned sleep on overnight. Summing over any set that grows — the container's pids, or one session's subagents — crosses a fixed threshold once the set is big enough, however idle each member is. Three idle tabs at ~300B each summed past 1024B and held the lock all night. The max is flat in N.
    - **The threshold was never the problem; the aggregation was.** Measured per 3s poll: a genuinely idle session writes **218–374B**, a mid-turn spinner 1.4–2.4KB, streaming 3.5KB+, with transcript flush spikes to 76–250KB. The 1024B default sits in the idle→spinner gap with ~4× headroom either side. (An earlier claim that idle writes 1–2KB was a misread *mid-turn spinner*.)
    - **Only pids in both consecutive samples count.** A pid appearing mid-interval has no baseline, so its lifetime total would read as one huge delta — and `resolv-sync.sh` respawns a `grep` every 3s, so fresh pids are constant.
    - Dead ends, for the record: **summing CPU ticks** failed for the same reason the byte sum did (scales with N, not a signal problem). **Transcript mtime** is chatty when idle (re-touched within 16s of nothing) *and* goes quiet 55s mid-turn — wrong in both directions. **Claude Code hooks** (`--settings` injecting `Pre`/`PostToolUse` set + `Stop`/`Notification` clear) are ground truth and flat in N, but no hook fires *during* extended thinking, a long stream, or a single long tool call, so they need a multi-minute timeout backstop and were rejected as too complex for what they bought.
    - An **empty sample** — session not started yet, exited, or a `docker` hiccup — reads as quiet and releases after `GRACE`. Ambiguous by construction, and deliberately resolved towards letting the machine sleep: a transient failure needs 10 consecutive polls to release, while the alternative bias is the overnight battery drain.
    - **Proactive suspend closes the lid-shut gap.** The `--what=sleep --mode=block` inhibitor is what keeps a long task alive across a lid close — that is wanted, so a task left running lid-shut finishes. But logind fires the lid-close suspend exactly **once**; blocked while the lock is held, it is dropped and never retried when the lock later releases. So a task that finishes a few minutes *after* the lid was shut used to strand the machine awake and draining till morning (this was the overnight bug's second half — the busiest-process fix makes the lock *release* when idle, but nothing re-triggered the swallowed suspend). The guard therefore re-issues it: on going idle it runs `systemctl suspend` itself, but only when it is unambiguously wanted — lid actually shut (`/proc/acpi/button/lid/*/state`), **no** external display connected (`/sys/class/drm/*/status` on a non-`eDP`/`LVDS`/`DSI` output → clamshell/docked means "keep working"), and **no** other `claude-code` inhibitor still held (a sibling tab is busy). It runs host-side as the user, so `systemctl suspend` carries the active session's polkit; it fires every idle poll, so an attempt blocked by some non-cc inhibitor simply retries once that clears. `SLEEP_GUARD_LID_SUSPEND=0` opts out. DEAD END (do not retry): switching the inhibitor to `--what=idle` — that makes a lid close *always* suspend, killing a running task mid-flight; the block must stay and the re-trigger is the fix. The one-shot lid-suspend is why an idle-timeout alone (e.g. KDE "suspend after N min") is not a substitute: a machine configured for lid-close-only, or with a long/disabled idle timer, would otherwise never sleep after a lid-shut task ends.
- Uses Docker's default seccomp profile and AppArmor confinement (no custom overrides).

## Session isolation (per-project config dirs)

Claude Code runs a **background-agent daemon** — a singleton arbitrated by `daemon.lock` in its config dir, owning background sessions, background subagents, workflows and the `claude agents` view. `cc` used to bind-mount one host `~/.claude` read-write into *every* container, which broke two ways:

1. Two concurrent `cc` sessions fought over one `daemon.lock`. Containers have separate PID namespaces, so the lock's `pid`/`procStart` liveness fields are meaningless across them — each daemon read the other's pid against its own `/proc` and displaced it, in a loop (`daemon.log`: `lockfile now held by pid=… — displaced, yielding`).
2. Every container could read every other project's transcripts, prompt history and paste cache.

The fix uses the two independent path resolvers in the Claude binary:

| Env var | Resolves | `cc` points it at |
|---|---|---|
| `CLAUDE_CONFIG_DIR` | everything: `daemon.lock`, `daemon/`, `sessions/`, `jobs/`, `projects/`, `file-history/`, `history.jsonl`, `.claude.json`, `settings.json`, `plugins/` | `~/.claude-sandbox/<slug>/` (this project only) |
| `CLAUDE_SECURESTORAGE_CONFIG_DIR` | **only** `.credentials.json` | `~/.claude-shared/` (all projects) |

So state is private per project while one login token serves every session. `<slug>` is `$PWD` with non-alphanumerics → `-`, the same scheme Claude uses for `~/.claude/projects/`.

Assets that *should* be shared (`settings.json`, `keybindings.json`, `CLAUDE.md`, `plugins/`, `skills/`, `agents/`, `commands/`, `hooks/`) live in `~/.claude-shared/` and are **symlinked** into `$CLAUDE_CONFIG_DIR` by `docker-entrypoint.sh` on every launch, since Claude only looks for them under the config dir. Claude rewrites `settings.json` atomically (temp file + rename), replacing the symlink with a real file — the entrypoint folds that edit back into the shared copy before relinking, so an in-session settings change isn't lost.

`~/.claude` and `~/.claude.json` no longer exist after migration; `cc` refuses to launch until `~/.claude-shared/.migrated` is present.

## One container per project (same-project concurrency)

Per-project config dirs fix *cross*-project collisions. They do nothing for two terminals on the **same** project — and that has to work.

Claude already supports it: the binary has a `[concurrentSessions]` pid registry, and the daemon arbitrates via `daemon.lock`, storing `pid` + `procStart` read from `/proc/<pid>/stat`. Both mechanisms assume all sessions **share a PID namespace and a `/tmp`** — true for two terminals on the host, false for two containers. Two containers can therefore *never* share a config dir: each reads the other's pid against its own `/proc`, concludes the daemon is dead, and displaces it — forever. The daemon's control socket (`/tmp/cc-daemon-<uid>/`) is container-local too, so adoption can't work either.

So `cc` stops handing Claude an environment it can't cope with. Instead of one container per terminal:

- **One long-lived container per project**, named `cc-<basename>-<hash of $PWD>`, started detached with `sleep infinity` as PID 1 (`--init`, so exec'd sessions' zombies get reaped).
- **Every terminal attaches with `docker exec`**, re-entering `docker-entrypoint.sh` and inheriting `CLAUDE_CONFIG_DIR` etc. from the container's env.
- Claude therefore sees exactly what it sees on the host: one PID namespace, one `/tmp`, one config dir, one daemon, N sessions. Its own arbitration does the rest — shared `/resume`, prompt history and background jobs across terminals, for free.

**Startup is not instant.** `docker run -d` returns as soon as PID 1 exists, but the entrypoint still has to `useradd`, build the symlink farm and chown the session dir. `cc` therefore waits for the container to be *ready*, and readiness means **a process whose command line is exactly `sleep infinity`** — which only exists once the entrypoint has `exec`'d. The exactness is load-bearing: while the entrypoint is still working its argv is `/bin/sh …/docker-entrypoint.sh sleep infinity`, and PID 1 (`docker-init`) carries `… -- …docker-entrypoint.sh sleep infinity` forever, so a substring match would call a half-set-up container ready.

**Container lifecycle** is reference-counted with `flock` on `~/.claude-sandbox/.locks/<slug>.lock`:

- each terminal takes a **shared** lock (fd 200) for its lifetime — a refcount, not a mutex;
- a `<slug>.boot.lock` **exclusive** lock serialises the check-and-create, so two terminals started at the same instant don't both `docker run` the same name;
- on exit a terminal drops its shared lock and tries to take the lock **exclusively**, which can only succeed if nobody else holds it — so exactly one terminal (the last one out) stops the container. While it holds that lock a starting `cc` blocks on its `flock -s`, so nobody can attach to a container being torn down.
- The locks live in `~/.claude-sandbox/.locks/`, **not** in `$SESSION_DIR` — that dir is bind-mounted rw into the container, so a sandboxed Claude could delete the lock file and break the never-unlink invariant (below) from the inside.
- `cc` traps **SIGHUP and SIGTERM** and exits through the normal path. Bash treats both as fatal and dies *without* running the `EXIT` trap — so closing the terminal window would otherwise skip the last-one-out teardown, stranding the container and orphaning a `sleep-guard.sh` that still holds a sleep inhibitor.

`CC_FORCE_NEW_SESSION=1` is no longer needed for a second terminal. It now means "clean slate": its own container *and* its own ephemeral config dir (hence its own daemon — no collision), discarded on exit. It also gets its **own** `/tmp/cc-{fuse,mask}.<hash>.eph.<pid>` scratch dirs: sharing the project's would mean its startup ("clear anything a crashed session left behind") and its exit both tear down the *real* container's live FUSE mount, unmasking `.ccignore`'d files under a running session.

**Unmount the FUSE view before killing the sidecar.** Killing the server first leaves the mount in the kernel's mount table with every `stat()` on it returning `ENOTCONN` — so `mountpoint -q` reports "not a mountpoint" for a directory that still is one, the unmount is skipped, and the mount is orphaned on *every* exit. The next launch of that project then dies trying to `rm -rf` a live mountpoint. `cc` therefore reads `/proc/self/mounts` directly (`fuse_mounted()`), never `mountpoint(1)`, and unmounts before `docker rm`. It also **refuses to `rm -rf` a path that is still mounted**: `$FUSE_ROOT/mnt` is a passthrough view of the project, so deleting it while mounted would delete the real files through it.

**`.ccignore` caveat:** redaction is fixed at container creation — the sidecar reads the rules once. Since the container outlives a single terminal, `cc` **refuses to attach** if `.ccignore` changed since it started, or if the running container has no sidecar at all (which is also what a container created by an older `cc` looks like); attaching under stale or absent rules would be a leak. Close all of the project's sessions and relaunch to apply a change.

## Host-executed config guard

The sandbox's real boundary is not the container — it is **what the host runs later**. A session that can write a file some unsandboxed host process executes on its own was never sandboxed (the failure mode behind the Nov 2025 Cursor/Codex/Antigravity escapes: `.claude` hook config, VSCode task config, git metadata indirection). Measured from inside the sandbox, `cc` had four of these.

The guard reuses the `.ccignore` machinery rather than adding a parallel mechanism. One rule tuple `(neg, pattern, anchor, action, immune)`, one matcher, one `_verdict()` loop; project `.ccignore` rules load as `anchor=bare|exact, action='redact', immune=False` and behave exactly as before.

- **`.git/config` is content-validated, not blocked.** Blocking it outright would break `git remote add` and `push -u` in the sandbox; *redacting* it would break git entirely, since git reads it on virtually every command — hence the `protect` action (read through, deny writes). Git never writes `config` in place: it writes `config.lock` and renames over the target, so the **rename is the write**, and validating there needs no buffering of `write()` calls. A write is refused only if it *adds or changes* an entry naming a command the host would run (`core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `alias.*`, `filter.*.clean`, …). Compared against the current file, not judged absolutely — a repo that already has a git-lfs filter is the user's own host-side config, and adding an unrelated remote must not trip over it. Unreadable or non-UTF-8 input fails closed.
- **`include`/`includeIf` are refused like a command key**, and the parser follows git's grammar. Both are audit fixes and both are load-bearing: an included file can declare `core.hooksPath` (or the `.gitattributes` filter/diff/merge drivers) that the validator never sees, and git's parser **resumes scanning after `]`**, so `[core]hooksPath = x` on one line is a real setting — `_dangerous_entries` must parse the remainder rather than treat the line as a bare header. Only *newly added* includes are refused, so a pre-existing one (the user's own host-side config) still works.
- **Git's own paths are matched structurally, in `_git_sensitive()`, not by patterns.** Submodules put config and hooks under `.git/modules/<name>/` (arbitrarily deep, since submodules nest) and worktrees under `.git/worktrees/<name>/`; a tail rule cannot express that. It shares `_is_git_config()` with the write validator, so "what is a git config" is defined once. This is why `global.ccignore` lists `.vscode`/`.envrc`/… but *not* `.git/*`.
- **A git dir is recognised by layout (`HEAD`+`objects`+`refs`), never by the name `.git`.** `git init --bare`, `--separate-git-dir` and a `.git` gitfile holding `gitdir: ../store` all put config+hooks under a differently-named directory, which a name match misses entirely while the host still runs what they configure. `_is_git_config()` — not just `_git_sensitive()` — carries the structural test on purpose: `rename()` routes on it, so a bare repo's config reaches the *validator* instead of a blanket deny, and in-container `git worktree add` keeps working. The gitfile itself stays writable for the same reason; its target is guarded.
- **`link()` validates the source, not only the new name.** A hardlink is a second directory entry for the same inode and the VFS does not re-resolve it (a symlink does, which is why the symlink form was never a bypass). Guarding the target alone let an unmasked alias launder a protected inode — write `.git/config` directly, or read a redacted `.env` past the stub.
- **Why the `.git/hooks` read-only bind mount is not enough** (it stays as belt-and-braces): it is conditional on the directory existing **at launch** (`cc:286`) and covers only the top-level repo, so a repo cloned or `git init`ed mid-session gets nothing. Worse, it was bypassable without touching it at all — `.git/config` sits next to it and `core.hooksPath` redirects git straight past it.
- **`no-new-privileges`** is set on the main container. The image still ships setuid binaries (`su`, `mount`, `passwd`, `fusermount3`) and `NoNewPrivs` was `0`. Defence in depth — session caps are already empty — and deliberately **not** set on the FUSE sidecar, which needs `SYS_ADMIN` and `fusermount3`.

**Closed since, by the shared-config lock and the clipboard proxy** (both below). What remains open is the shared OAuth token under open egress (audit H3/H4) — see "Accepted risks".

## Shared config surface (cross-project pivot)

`~/.claude-shared` is mounted into every project's container, and everything in it auto-loads in every project's *next* session — so a write from one sandboxed repo reaches all of them. That is the widest blast radius in the design, and it is not covered by the FUSE guard (the guard is a view of the *project*, not of `$HOME`).

- **Assets are mounted read-only, individually** — `CLAUDE.md`, `hooks/`, `plugins/`, `skills/`, `agents/`, `commands/`, as nested `:ro` binds over the writable shared mount. The whole dir cannot be read-only: an OAuth refresh has to rewrite `.credentials.json`.
- **The entrypoint builds a per-project merge farm** for the four asset *directories*: a real dir holding one symlink per shared item, not one symlink to the shared dir. Shared items still load; anything created in-session lands in `$CLAUDE_CONFIG_DIR` and works immediately. Without this, a read-only mount would break `/agents`, skill authoring and `/plugin install` outright — the lock would read as a bug. Pruning removes only symlinks pointing into `$CLAUDE_SHARED_DIR`, so a project's own items are never touched. **State files need no special case** — a JSON writer does temp-file + rename, and the rename replaces the symlink with a real local file, which the farm dir permits. **Directories do**, which is why `farm_dir` also runs one level deeper on `plugins/{marketplaces,cache,data}`: a `/plugin install` has to `mkdir` *inside* those, and a symlink to the read-only shared dir refuses it.
- **`cc --unlock-shared`** (or `CC_UNLOCK_SHARED=1`) drops those mounts, which is how you deliberately promote an install to every project. Mounts are fixed at container creation, so `cc` refuses to attach in the *other* mode — in both directions — exactly like the stale-`.ccignore` refusal.
- **`settings.json` stays writable and is validated host-side instead** (`validate_shared_settings`, `cc-lib.sh`), on every launch, before any container reads it. Refused: `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`, `env.ANTHROPIC_{BASE_URL,API_KEY,AUTH_TOKEN}`, `statusLine.command`, and any inline `hooks.*[].hooks[].command` — the last being the exact bypass that makes a read-only `hooks/` dir insufficient, the same shape as `core.hooksPath` bypassing read-only `.git/hooks`. Locking the file was rejected: `/config` and theme changes are normal, and a lock would silently strand them per-project. This is prevention **at launch, not at write** — a poisoned file is caught before the next session loads it, which is the propagation step that matters, but H5 is therefore *mitigated*, not *fixed*.

## Clipboard: mediated, not handed over

The host Wayland socket used to be bind-mounted into the main container read-write and unmediated. It is there for one job — pasting an image *from* the host clipboard — but the raw socket also grants clipboard **writes**, and a write is host code execution at the user's next terminal paste: an embedded `ESC[201~` ends bracketed paste early, so the rest of the payload is interpreted as typed input.

`wayland-guard.py` runs in a sidecar (`${CNAME}-wl`, `--network none`, AF_UNIX only) and is the only thing that ever sees the real socket. It relays the wire protocol and:

- **refuses** `create_data_source`, `set_selection`, `set_primary_selection` and `start_drag` on all four clipboard interfaces — `wl_data_device{_manager}`, `zwp_primary_selection_*`, `zwlr_data_control_*`, `ext_data_control_*` — closing that connection. Dropping a request that allocates a `new_id` would desynchronise the client's object space, so closing is the only clean refusal;
- **hides nothing from the registry.** DEAD END, do not retry: an earlier version dropped `wl_data_device_manager` and `zwp_primary_selection_device_manager_v1` from `wl_registry.global`. That broke `wl-paste` outright — KWin advertises `ext_data_control_manager_v1` but *not* `zwlr_`, and this `wl-clipboard` build speaks neither, so it falls back to `wl_data_device_manager`. Every clipboard interface carries the read and the write half together; refusing the write *requests* is exactly as strict and costs no reads;
- **forwards everything else verbatim**, including `SCM_RIGHTS` fds, which is how clipboard content actually moves. `zwlr_data_control_manager_v1` is deliberately kept: it is how `wl-paste` reads a selection without keyboard focus.

Object→interface tracking needs no protocol database — `wl_registry.bind` carries the interface name as a string argument, and only a handful of factory opcodes need hard-coding.

**Host terminal select + Ctrl+Shift+C is unaffected**, and this is worth remembering before anyone "fixes" it: your terminal emulator is a *host* Wayland client and never comes through the proxy. Only a program running *inside* the container is filtered.

A denial logs `WLGUARD-DENY` on stdout; a host-side follower (`start_wayland_notifier`, `setsid` + pid file, killed by process group at teardown) turns that into a desktop notification, rate-limited to one per 30s. **Fail-soft, unlike the FUSE sidecar**: no host Wayland, or a proxy that won't start, means no socket is mounted at all — absent Wayland is not a security hole, so aborting the launch would be wrong, while falling back to the raw socket would be.

## DNS across host network changes (long-lived containers)

Docker freezes a container's `/etc/resolv.conf` at **creation** time. With short-lived per-terminal containers that was invisible — relaunching after a network change minted a fresh copy. Now the container is long-lived, so the moment the host switches wifi or attaches a VPN, its baked-in upstream nameservers become unreachable and **every attached session loses DNS** while the host still has it (routing/NAT stays fine — only name resolution breaks).

Docker already copies the host's **real per-link upstream nameservers** (from systemd-resolved's `/run/systemd/resolve/resolv.conf`) into the container — a *fresh* `docker run` tracks the network perfectly. The whole bug is that the long-lived container never refreshes that copy. So `cc` keeps it refreshed:

- **`cc` bind-mounts the host's `/run/systemd/resolve` directory read-only** into the container, plus `resolv-sync.sh`. The *directory* (not the file) is mounted on purpose: systemd-resolved swaps `resolv.conf` by atomic rename, so a *file* bind-mount would pin the old inode and go stale, while a *directory* mount always resolves the current inode. That directory also holds systemd-resolved's **Varlink control sockets** (`io.systemd.Resolve` and `io.systemd.Resolve.Monitor`); a read-only *mount* does not stop a `connect()`, and those sockets reach the host daemon in the host's namespace — an unauthenticated connect can drive host-side resolution and dump the host's full DNS/interface topology. `cc` therefore **shadows each socket with `/dev/null`** (a nested bind-mount; `connect()` → `ENOTSOCK`), so the directory mount tracks `resolv.conf` live while nothing in the sandbox can reach the host resolver daemon.
- **`start_resolv_sync` launches `resolv-sync.sh` once**, right after the container is ready, as a detached root `docker exec` (uid 0, bypassing the entrypoint, because it writes `/etc/resolv.conf`). It is started only on the create path under the boot lock, so exactly one watcher exists; it lives for the container's whole life — shared by every attached terminal — and is killed when the container is removed, so there is nothing to tear down. The watcher polls the mounted dir and copies the current upstreams into `/etc/resolv.conf` whenever they change, so a new lookup after a wifi/VPN switch uses the live servers.

**Why not a relay to systemd-resolved's `127.0.0.53` stub** (the earlier design)? The stub gives more precise split-DNS (routing domains), but it's on loopback, so reaching it needs a `--network host` root sidecar bound to the docker bridge gateway, and the main container has to talk to `<gateway>:53`. A **per-connection host firewall (Portmaster)** silently *holds* that `container→gateway:53` hop with no prompt to allow it — so the relay simply cannot work there — while it *permits* the container to query the real upstream servers directly (public or LAN). Syncing `resolv.conf` uses exactly that permitted path, needs no root host-netns sidecar at all (a security win), and still follows the host live. The trade is split-DNS precision: the container gets the real per-link servers and lets glibc pick, rather than systemd-resolved's routing logic — fine for a LAN plus one VPN, less precise for complex multi-interface split-DNS.

`notify()` is for **problems only** — a normal launch raises no desktop notification, so any popup means something needs attention. It exists because `cc` execs `claude`, whose TUI clears the screen within milliseconds, making a stderr line unreadable in practice; that argument justifies surfacing a *failure* (no systemd-resolved, watcher didn't start), never a success. Do not add a "working as intended" notification to any launch path — it fires on every launch and trains the user to dismiss the ones that matter. Best-effort — no `notify-send` or no desktop session (ssh, `cc … -p`) makes it a no-op.

Everything is **best-effort with a fail-safe fallback**: if the host has no systemd-resolved (no `/run/systemd/resolve/resolv.conf`), `cc` adds neither mount nor watcher and the container keeps Docker's default `resolv.conf`, frozen at creation — never worse than before, just not fixed, and `cc` says so. The watcher itself is conservative: it strips loopback nameservers (useless inside the container netns) and refuses to write a `resolv.conf` with no nameserver, so a transient bad read can't blank DNS outright. Already-running containers predate any of this; close the project's sessions and relaunch to pick it up.

## macOS support (Plan H)

`cc` runs on macOS with **any** Docker engine (Docker Desktop, OrbStack, Colima) — no VM dependency is baked in. The one thing macOS cannot do is host the Linux `cap-drop=ALL` FUSE **sidecar**: Docker Desktop refuses shared-mount propagation and blocks the unprivileged-userns FUSE path (measured — see `docs/FUTURE_TASKS.md` Gate B). So the redaction layer has **two modes behind one interface**, chosen once by `CC_FUSE_MODE`:

- **`sidecar` (Linux, unchanged):** `ccignore-fuse.py` in a `cap-drop=ALL` container, exposed by propagation. The verified, strongest-isolation path.
- **`single` (macOS, and Linux under `CC_SINGLE_CONTAINER=1`):** no sidecar. The container is created with `--cap-add=SYS_ADMIN --cap-add=SETPCAP --device /dev/fuse --security-opt apparmor=unconfined`; the **trusted** entrypoint (`entrypoint-fuse.sh`, baked) mounts the redacted view over the project path. The real project is exposed only at `/cc/real` under a root-700 parent, so the agent reaches it *only* through the redacting view. The mount dies with the container — no host-side `FUSE_ROOT`, no propagation, no unmount ordering. The residual "created cap-capable" surface is the documented, accepted R2 trade (agent capless-at-runtime, not `cap-drop=ALL`-at-creation).
  - **The `SYS_ADMIN`/`SETPCAP` drop happens per session, in `cc`'s `docker exec`, not at PID 1.** `docker exec` gives every session the *container's* configured cap set — it does **not** inherit PID 1's reduced bounding set — so a `setpriv` on the entrypoint's `sleep infinity` is invisible to the agent. So in single mode `cc` enters the session as **root** (no `--user`) and runs `setpriv --bounding-set -sys_admin,-setpcap gosu <uid>:<gid> …` itself: `setpriv` needs `CAP_SETPCAP` *effective* (which root has, but a `--user`-entered uid-1000 session does not), drops the two mount caps from the bounding set, then `gosu` drops to the capless agent. `security-test.sh` (itself a `docker exec`) asserts `CapBnd` lacks both. Sidecar mode's container never had `SYS_ADMIN`, so it keeps the plain `--user` entry.

The three interface functions are `prepare_redaction` / `verify_redaction_attach` / `teardown_redaction` (`cc-lib.sh`); `cc` calls only those. `CC_SINGLE_CONTAINER=1` is a **test vehicle**, not a user feature: it forces the entire macOS topology on Linux so `check.sh` and `security-test.sh` exercise it here. **Both modes must pass the full `security-test.sh`** (run it once normally, once under `CC_SINGLE_CONTAINER=1`); the suite auto-detects single mode from the container's inherited `CC_FUSE_INTERNAL=1` and adjusts the two expectations that differ (AppArmor is `unconfined`; `/cc/real` exists and must be unreachable).

**All OS branching lives in one file, `cc-portable.sh`** — sourced by `cc`, `cc-lib.sh`, `build-bg.sh`, `sleep-guard.sh` before anything platform-specific. It sets `CC_OS`/`is_macos`/`CC_FUSE_MODE` and provides the shims every other host script calls instead of GNU-only tools:

- `lock_fd` — replaces `flock(1)`. Darwin flocks the *inherited fd* with perl (`open(F,">>&=",FD)` + `flock`), so the open-file-description lock semantics are identical: the lock persists after the shim returns (the shell keeps the fd open) and releases on `lock_fd -u` or `exec N>&-`. Every `flock` call site switched to it.
- `hash8` (`sha256sum`→`shasum -a 256`), `detach_pgrp` (`setsid`→perl `setsid`+`exec`), `notify_desktop` (`notify-send`→`osascript`), `preflight_platform` (engine/perl/bind-mount checks; Linux no-op).

**The portability contract** (header of `cc-portable.sh`, enforced by `check.sh`): host-side scripts are **bash-3.2/BSD-clean** — stock macOS ships bash 3.2 + BSD userland + system perl, **no brew deps**. GNU-only shimmed tools (`flock setsid sha256sum grep -P notify-send`) and bash-4isms (`declare -A`, `${var,,}`, `readarray`) are allowed ONLY inside `cc-portable.sh`'s `linux` branches. `check.sh` greps for violations (comments stripped; `cc-portable.sh` and `check.sh` exempt), and unit-tests the shims by **forcing the perl/darwin paths on Linux** (perl is identical) — so `./check.sh` on this repo proves the macOS code paths without a Mac. The Wayland notifier's raw `setsid`/`notify-send` are the one allowed exception (structurally Linux-only; it runs only when `!is_macos`) and show as advisory warnings.

**Sleep guard:** `caffeinate -is` on macOS instead of `systemd-inhibit`. No proactive-suspend port — macOS re-evaluates sleep when the assertion releases, so the Linux one-shot-lid-suspend bug (see `sleep-guard.sh`) does not exist there; `SLEEP_GUARD_LID_SUSPEND` is documented Linux-only. Lid-close on battery still sleeps (OS limit). The busiest-process/both-samples logic is unchanged — its `declare -A` was rewritten as an awk delta-join (`busiest_delta`), the only bash-4 construct in the file.

**Clipboard:** a **pbpaste bridge**, one-way by construction (mirrors the Wayland guard's read/write asymmetry). `clipboard-bridge.sh` (host, POSIX sh) watches a spool dir bind-mounted at `/cc/clip`; the entrypoint installs container-side `wl-paste`/`xclip` reader shims (drop a request, read the response) and `wl-copy`/`pbcopy` shims that leave a deny marker and fail. The host answers reads with `pbpaste`/an `osascript` PNG extraction and **never calls `pbcopy`**; a deny marker becomes a rate-limited `osascript` alert. Started/stopped exactly like the Wayland notifier, including the load-bearing `200>&- 201>&-`.

**DNS:** skipped on macOS (one info line, no notification) — the engine VM already tracks the host resolver, so there is nothing to sync.

**Fresh install:** `migrate-sessions.sh` on a Mac with no legacy `~/.claude` bootstraps the `~/.claude-shared` skeleton + `.migrated` directly (`--apply`), instead of refusing because there is nothing to migrate.

**Still open — on-hardware VERIFY (Mac only, cannot be tested from Linux):**
- Which reader Claude Code invokes for image paste inside a Linux container. `add_clipboard_bridge_args` currently sets `WAYLAND_DISPLAY` to route it to the `wl-paste` shim; if the Mac test shows it uses `xclip`/`DISPLAY`, that is a **one-line** flip (both shims are installed). The mechanism is built; only the trigger env is provisional.
- File ownership presented by DD/OrbStack **virtiofs** bind mounts, which the root-served FUSE passthrough reads through. The redaction guarantee is uid-independent (`_deny_if_masked` raises EACCES regardless), so this affects passthrough reads only; covered by the Mac redaction probes.
- The README/head-to-head "macOS ❌" rows flip only **after** these pass on hardware.

## Key Design Decisions

- Project is mounted at the **same absolute path** as on the host, so Claude's path-keyed project configs resolve correctly.
- Claude's config is split: per-project `~/.claude-sandbox/<slug>/` + shared `~/.claude-shared/` (see above).
- All capabilities dropped (`--cap-drop=ALL`); default CMD is `claude --dangerously-skip-permissions`.
- **Auto-update check**: each launch compares the installed version (`/etc/claude-code-version`, falling back to `claude --version`) against the latest release, and offers a background rebuild while you keep using the current image.
- **Every host-side background process `cc` spawns must close fds 200 and 201** (`200>&- 201>&-` on the `&` line). Those are the project's shared lifecycle lock and the boot lock. A child that inherits fd 200 and outlives its `cc` — `sleep-guard.sh`, the `wayland-guard` notification follower, anything added later — keeps the shared lock held, so the last terminal out can never take it *exclusively*, `teardown_container` never runs, and the container plus both sidecars are stranded until a manual `docker rm -f`. Shipped once without it on the notifier: it stranded the containers of **every** project whose sessions had been closed, and the symptom (`docker ps` full of live containers with no sessions) looks nothing like a locking bug. `docker exec -d` children are exempt — the docker client exits immediately and the process lives in the container.
- **Lock files are never unlinked.** `build.lock` and `~/.claude-sandbox/.locks/*` are tested in place with `flock -n`. Deleting a lock file whose inode another process holds `flock`ed lets the next process create a *fresh* inode and lock that instead — two "exclusive" holders at once. This is also why the lifecycle locks are kept out of the container-mounted session dir.
- **`tput` is guarded with `|| true`.** It exits 10 when stdout isn't a tty, and `cc` runs under `set -e` — unguarded, a redirected run (`cc claude -p '…' > out.txt`) dies before the session starts, and the copy in the `EXIT` trap overwrites the session's real exit code. `read` is guarded for the same reason.
- **`leftArrowOpensAgents: false` — do not re-enable.** It is a **global-config** key (`.claude.json`, sibling of `copyOnSelect`/`defaultToAgentsView`), **not** a `settings.json` key — putting it in `settings.json` is silently inert. `.claude.json` is per-project here, so `cc` re-asserts it every launch via `pin_global_config` (`cc-lib.sh`) — **not** via `~/.claude-shared/claude-json.seed`, which lands on a project's *first* run only and therefore never reaches a project that already exists. The pin writes only when the value is missing or wrong: a live session holds this file in memory and rewrites it wholesale, so losing the pin (re-applied next cold start) beats clobbering that session's state. Add future global-config keys to its `PINS` dict. From a *foreground* session `←` does not mean "go back", it means **background this session**, and with a turn in flight it takes the binary's `abort-then-fork` path: checkpoint, then abort the in-flight Workflow's and every subagent's `AbortController`, then respawn the conversation as `--resume … --fork-session`. Workflows run **in-process** in a Node `vm` context inside the session, so nothing in them survives that fork; the carry-over gate requires `isBackgrounded===true` on **every** subagent in the tree, and is a tree-wide AND whose verdict is written to all ids — but `Task` subagents are built `isBackgrounded:false`, so one live foreground child poisons the parent workflow and its siblings. A workflow *with live agents* — the only case that matters — is therefore structurally non-carryable: never checkpointed, so absent from `adopt.json`, so nothing resumes it. Sessions opened *from* the agent view take a clean `detach` instead and are unaffected, which is why the bug only ever hits foreground sessions. **The sandbox is exonerated — do not re-investigate it.** Verified: the daemon socket path `/tmp/cc-daemon-<uid>/<sha256(realpath($CLAUDE_CONFIG_DIR))[0:8]>/control.sock` matches its computed value at mode 0700/own uid (the binary hard-fails otherwise); `jobs/`, `sessions/`, `projects/`, `daemon/` are all genuinely per-project, none of the carry-over path reads `~/.claude-shared`; workflow scripts live under `$CLAUDE_CONFIG_DIR/projects/…/workflows/`, outside the FUSE view, so no realpath rejection; and `daemon.log` has never once logged `[adopt] write failed`/`[adopt] stale` — the machinery never engages at all. The view stays reachable via `claude agents`, `/background` and `--bg`; unbinding `left` in `keybindings.json` does **not** work. Each press also mints a **new session id** whose transcript holds only `ai-title`+`agent-name` — those 200–300-byte duplicates cluttering `--resume` are one per press, not corruption. Do **not** reach for `CLAUDE_CODE_DISABLE_AGENT_VIEW=1`/`disableAgentView` as a bigger hammer: its own schema says it disables "`claude agents`, `--bg`, /background, the on-demand daemon", and the reject path is `process.exit(1)`, not a no-op. It leaves in-process `Task` subagents and Workflows working, but costs every background *session*. A lost run resumes with `Workflow({scriptPath: …, resumeFromRunId: 'wf_…'})` — completed agents replay from the run's `journal.jsonl`.
- **`bg adopt: adopted=0 respawned=0 dead=N` in `daemon.log` is expected, not a bug.** It is the background-agent supervisor re-adopting workers left by a *previous* supervisor, keyed on `roster.json`'s `{pid, procStart}`. `cc` recreates the container, so the PID namespace is new and the container-local `/tmp/cc-daemon-<uid>/` is gone — every rostered pid really is dead. It runs once at daemon start and is on no live code path. Likewise `idle 5s with no clients — exiting` can never fire under running work (the timer arms only when leases *and* live handles are both zero), and `bg settled … (killed)` always names a `(spare)` — spare-pool churn. All three look alarming and have each cost a full investigation.

## Security Posture

**Hardened against container escape:** seccomp (mode 2), AppArmor (`docker-default` enforce), `--cap-drop=ALL` (only SETUID/SETGID/CHOWN/DAC_OVERRIDE/FOWNER added back for the entrypoint), `no-new-privileges`, PID namespace isolation, no Docker socket, no host block devices, no writable `/proc/sys`.

**Read-only mounts for host-executable paths** — both would be host code execution if writable:
- `.git/hooks` — would run on the host at the next `git commit`
- `~/.claude-shared/hooks` — would run on the host in a future Claude session

Neither is sufficient alone: a read-only `hooks/` is bypassable by whatever *chooses* the hook path (`core.hooksPath` for git, inline `hooks` commands in `settings.json` for Claude). See "Host-executed config guard" for what covers git, and "Shared config surface" for the Claude-side equivalent — `validate_shared_settings` refuses inline `hooks[].command` host-side each launch.

**Cross-project isolation:** a container mounts only its own `~/.claude-sandbox/<slug>/`, so it cannot read another project's transcripts, prompt history, jobs or pasted content. `.claude.json` is pruned per project (globals + that project's entry, including its `mcpServers`); `githubRepoPaths` is scoped so other projects' paths don't leak either.

**Accepted risks (required for the workflow):**
- **Open egress + a durable shared credential.** `~/.claude-shared/.credentials.json` is same-uid readable and egress is unrestricted, so an injected session can exfiltrate the account OAuth token with no host trigger (audit H3/H4). Deliberately not fixed: the token cannot be made unreadable — Claude needs it — and a default-deny allowlist conflicts with the sandbox's whole purpose, building untrusted repos that fetch from arbitrary registries. **Rotate the token if an untrusted session has run.**
- Wayland socket mounted, but **proxied**: clipboard reads only, writes refused (see "Clipboard: mediated")
- `host.docker.internal` routable to the host network stack
- Project directory writable (by design)
- The live-DNS sync bind-mounts the host's `/run/systemd/resolve` directory **read-only** into the main container and runs `resolv-sync.sh` there as a detached **root** `docker exec` (uid 0) so it can rewrite the container's own `/etc/resolv.conf`. That's a root process *inside the already-privileged-for-setup main container*, not a new host-netns component — the earlier `--network host` relay sidecar is gone entirely, so nothing cc runs touches the host network namespace anymore. The mount exposes only the host's public resolver config (world-readable `resolv.conf`), read-only — and systemd-resolved's Varlink sockets in that dir are **shadowed with `/dev/null`** so a sandbox process cannot `connect()` to the host resolver daemon through the read-only mount (a read-only mount blocks writes, not socket connects).

## Build & Run

```bash
# One-time migration to per-project sessions (required before cc will launch)
./migrate-sessions.sh          # dry run — prints every copy/write/delete
./migrate-sessions.sh --apply  # commit; deletes ~/.claude and ~/.claude.json

# Build image (happens automatically on first run)
docker build -t claude-code-sandbox .

# Run from any project directory
/path/to/cc                    # default: launches claude
/path/to/cc bash               # override CMD to get a shell
/path/to/cc claude --resume    # pass args through
CC_FORCE_NEW_SESSION=1 /path/to/cc   # clean-slate throwaway session

# Rebuild with custom packages
docker build --build-arg CUSTOM_PACKAGES="golang ruby" -t claude-code-sandbox .

# Force reinstall a specific Claude Code version (Docker caches by version)
docker build --build-arg CLAUDE_VERSION=2.1.71 -t claude-code-sandbox .
```
